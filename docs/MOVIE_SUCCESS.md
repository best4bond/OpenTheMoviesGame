# How a movie's success and box-office revenue are computed (The Movies, MoviesSE.exe 2006 patched build)

Reverse-engineered from `CProjectSuccess_Recompute` (`FUN_005dedc0`) and helpers, `CProjectIncome_CreateForPlayerProject/AIProject`, and `Data\releasing_movies.ini`. Companion to `MOVIE_QUALITY.md`.
Labels: **[code]**, **[data]** (ini), **[guess]**.

## 1. Overview **[code]**
(`Qm`, the movie's quality, is the runtime-weighted mean of the per-shot ratings plus a pre-production term, frozen when the movie enters post-production: `MOVIE_QUALITY.md` section 7.)
After release a movie has **quality** `Q` (0..1, see `MOVIE_QUALITY.md`) and a **success** value `S` (>= 0, not capped at 1) stored in `CProjectSuccess+0x90`. `S` decides the revenue: `total = revenue_base + revenue_multiplier * S^2`.
`CProjectSuccess_Recompute` is the same shape of formula as the quality rating: a base value (the quality) plus production-independent *market* factors with a diminishing-returns bonus.

## 2. The formula **[code + data]**
```
Qm = CProject_GetQualityWithAwardBoost(project)          // quality incl. award boost; if Qm is outside [-1e-6, 1.000001] it is replaced by 1.0
PI = 1.0 + (1.4 - 1.0) * PublicInterestFactor(...)         // public_interest_min/max            -> +0x94
SR = CastStarRatingsFactor                                 // star_ratings_of_cast_min/max 0.8..1.2 -> +0x98
GP = GenrePopularityAndSaturation(genre)                   // 0.9..1.2 x saturation (0.8..1.0)   -> +0x9c
BO = BoredomFactor                                         // 0.8..1.0                           -> +0xa0
TP = TechPioneeringFactor                                  // 1.1 if pioneering else 1.0         -> +0xa4
P  = TP * SR * GP * BO * PI
x  = ( (P - 1) - 2 * (Qm - 0.5) * 0.12 ) * 0.8             // success_overall_shifter_mid_point 0.5, success_overall_max_shifter 0.12, success_overall_max_adder 0.8
g(x) = x                                  if x <= 0        // linear, uncapped downward
g(x) = sum_k min(rest, 0.1) * 0.8^(k+1)   if x  > 0        // diminishing: chunks of 0.1, each worth 80% of the previous, max +0.4
S  = max(0, Qm + g(x))                                     // note: NO upper clamp (S can exceed 1.0; up to about Qm + 0.4)
```
(The same loop as `CQualityRating_Compute`; only the constants differ: quality uses mid point 0.4 / shifter 0.1, success uses 0.5 / 0.12; both use adder 0.8, chunk 0.1, ratio 0.8.)
For the **AI studios' projects** (project pointer null) the factors that need a project use neutral defaults: `PI = FUN_005dd2d0`, `GP = 1.0`, `BO = 1.0`, ratings from the studio record.

## 3. The factors
* **Public interest** `PI` (`CProjectSuccess_ComputePublicInterestFactor`, `FUN_005dcfd0`, see section 3b): `PI = 1.0 + 0.4 * F` (`public_interest_min/max`), where `F` in 0..1 measures how much **publicity** (PR) the movie got compared with its quality. A movie with no PR has F = 0 -> PI = 1.0 (neutral); PR can only help.
* **Cast star ratings** `SR` (`CProjectSuccess_ComputeCastStarRatingsFactor`, `FUN_005de8f0`): take the cast stars' ratings sorted high to low (`CProjectSuccess_CollectCastStarRatingsSorted`, `0x5DE6F0`: every cast star plus the director if a star; `...AI` at `0x5DE800`), then `sum = Σ clamp01(w_k * rating_k)` with the weight **squared each step**: `w_0 = star_ratings_proportion = 0.7`, `w_{k+1} = w_k²` -> **0.7, 0.49, 0.24, 0.058, 0.003 ...** (not a geometric series: the third and later stars barely count). `x = sum / (Qm' * 3 - 0.3)` with `Qm' = Qm` (or 0.2 when Qm < the floor constant `D1C488`), clamped 0..1, then `SR = 0.8 + (1.2 - 0.8) * x` (**0.8..1.2**). Higher-quality movies need bigger stars to reach the same bonus.
* **Genre popularity and saturation** `GP` (`Release_ComputeGenrePopularityAndSaturation`, `FUN_005dd3d0`): `GP = (0.9 + 0.3 * trend) * (0.8 + 0.2 * (1 - saturation))` where `trend` is the audience taste for the movie's genre (`AudienceTaste_GetGenreTrend`, 0..1; award bonus 10 replaces it) mapped through `genre_popularity_min/max` (0.9..1.2), and `saturation` (0..1) is the genre saturation tracker (section 3e) with `genre_boredom_bound 0.8` as the floor. Range 0.72..1.2.
* **Boredom** `BO` (`CProjectSuccess_ComputeBoredomFactor`, `FUN_005de3f0`): `BO` is the mean over the movie's **sets, cast members and director** of `(1 - b) * (1 - bound) + bound`, with `bound = 0.8` (`set_boredom_bound`, `star_boredom_bound`), so it ranges 0.8..1.0. Details in section 3c.
* **Technology pioneering** `TP` (`CProjectSuccess_GetTechPioneeringFactor`, `FUN_005dd570`): `TP = technology_pioneering_bonus (1.1)` if the studio reports an active pioneer technology for the movie's date, else 1.0 (`technology_min/max 0.7..1.0` are loaded but unused - see section 3d). **Confirmed by play: researching a film technology is what grants it** (the player's 1931.748 release got 1.1 right after a research). The player-studio check is `CStudioPlayer_HasActivePioneerTechnology` (`0x518D00`, vtable slot 0x88, called with the project's date at `project+0x2C8`): it walks the research items and returns true if any item is in the **`moviemaking`** research category (`ResearchCategory_NameToEnum("moviemaking")`), is researched (`FUN_0049C760`), and its two stored dates bracket the movie's date (item `+0x134` compared one way and item `+0xA4` the other, i.e. a window *[research date, research date + pioneer period)* - the comparison direction and what exactly `+0xA4` holds were read from the generic time comparators `FUN_0043B6E0/0043B680` and are not verified; the window length is therefore unknown). Only moviemaking-category technologies count (not e.g. set or stunt research). AI studios use their own check (`CStudioAI` vslot 0x88, `0x5149D0`, not decoded).

## 3c. Boredom in detail **[code + data]**
**Ingredients averaged** (all weighted equally, N = count; if N = 0 then BO = 0 and the report values 0):
* every **set** of the project (project list +0xac; `FUN_004df220` gives the set, `FUN_004d3720` its current boredom `b`), bound `set_boredom_bound` (global `E54BFC`);
* every **cast member** (star or extra; `FUN_005dd700`): `b = ` the character's boredom (`CStar` vslot 0x254 -> object at `star+0xBE8`; `CExtra` object at `extra+0xA94`), bound `star_boredom_bound` (`E54C04`) - extras use the same bound;
* the **director** if present, same as a cast member.
The costume and genre bounds (`costume_boredom_bound`, `genre_boredom_bound`) are loaded but **not used in this function** (genre repetition is handled by genre saturation, section 3, and `UnweightedGenre/Stars/SetsBoredom` in the save data are the display values: mean set boredom -> `+0xAC`, mean cast boredom -> `+0xB0`, overall mean -> `*param_2` for the report screen).
With **award bonus 3** active every `b` is multiplied by that bonus value (clamped 0..1) first.
So a movie whose ingredients are all completely fresh (b = 0) gets BO = 1.0, and one built entirely from totally over-used ones (b = 1) gets 0.8; a single bored star among many people barely matters.

**What a boredom value is**: a time-decaying float object `{ stamp, value0, rate }` (`FUN_00494fc0`): `b(t) = clamp01(value0 * 2^(-(t - stamp)/halfLife))` (rate stored by `FUN_00495060` as `ln(0.5)/halfLife` using the game clock `DAT_00E4FA4C`). **Adding** (`FUN_004950a0`): `value0 = b(now) + amount; stamp = now`.
**Half-lives and boosts** come from `Data\global.ini` (time unit: **years** of game clock, see 3e):
| object | halflife | boost per use | where stored |
|---|---|---|---|
| set | **3** | **0.1** x the set's own `boredom` ini field (`set+0x604`; default 0) | global map `DAT_0104AD74` keyed by set name (saved) |
| star/extra | **4** | **0.3** (`[star] boredomboost`; extras use the same value via `CStaff_GetBoredomBoost`, `0x586360`) | `CStar+0xBE8`, `CExtra+0xA94` |
| genre | **2** | **0.15** (used by the saturation tracker, not this factor) | `GenreSaturationTracker` |
(`[setdressing]` and `[backdrop]` sections also have halflife 1 / boost 0.5.) `releasing_movies.ini [boredom] star_boredom_increase 0.15` is loaded into the release tuning table but I found no reader in this path - the live star increment is the `[star] boredomboost`.

**When boredom is added**: at release, `Release_PushGenreSaturationEntry` (`0x5AEB60`): for each project object of class 4 (a set) `FUN_004d2940(amount = 1.0 [x award bonus 3])` -> adds `clamp01(amount * set.boredom_field)`; for each cast member and the director (if a star) `FUN_00585880 / FUN_0056fae0` (`+0.3`, `+extra rate`); then it pushes the genre to the saturation tracker. So **every released movie makes its sets and stars about 0.3 (stars) / 0.1 (sets) more boring, decaying with a 4 / 3 time-unit half-life**.
**Pending-use anticipation** (`FUN_004d3750`, used for planning screens, not the success calc): a set's effective boredom also adds `_DAT_0104ABE8 (set_adjusted_boredom_factor) * set.boredom_field` for every other studio project that is currently in production and uses the same set (excluding the given project).

## 3e. Genre saturation tracker (decoded) **[code + data]**
Singleton `GenreSaturationTracker` (`GetInstance` `0x44BC70`, config `GenreSaturationTracker_LoadConfig` `0x44C2F0`) holding a map (`DAT_00F88684`, saved in the savegame; restored by `FUN_0051BE40`) from a **genre-set key** to a time-decaying value (the same `DecayValue` object as boredom, see 3c).
* **Key** (`GenreSet_GetKey`, `0x44D2C0`): the movie's genre list (`FUN_005C48C0`) is packed into a multiset bitfield: each genre `g` adds `1 << (3*g - 3)` (a 3-bit counter per genre). So saturation is tracked **per genre combination**, not per single genre: a Comedy/Romance mix does not saturate Comedy alone.
* **Push** (`GenreSaturationTracker_Push`, `0x44D120`), called once per release:
  ```
  years = (now - 1920 years)                        // game clock in years
  if years <= 10: return                            // nothing is recorded before 1930
  ramp  = clamp01((years - 10) * 0.1)               // linear 0..1 from 1930 to 1940
  amount = genreBoredomBoost * ramp * weight        // [genre] boredomboost 0.15; weight = 1.0, or award-bonus-3 value for the player's release
  existing entry: value = current(now) + amount, stamp = now      // DecayValue_Add
  new entry:      value = amount, half-life = [genre] boredomhalflife (2)
  ```
  The player's movies (`Release_PushGenreSaturationEntry`, `0x5AEB60`) **and every AI studio release** (`Release_PushGenreSaturationEntry_AI`, `0x5A2B80`, genre from project+0x10C, weight 1.0) push into the same tracker. Compiled-in defaults were boost 0.25 / half-life 0.1; the live values come from `global.ini [genre]` (0.15 / 2).
* **Query** (`GenreSaturationTracker_Query`, `0x44C700`): `saturation = clamp01(decayed value)` for the key, 0 if the genre combination has never been pushed.
Consequences: each release of a genre combination adds 0.15 (after 1940) that halves every **2 years** (the clock unit is years: the threshold constant 1920 and the 10/0.1 ramp only make sense in years - inferred from the constants, not from a unit table). So about seven same-genre releases in a short window (player + all AI studios) saturate it (S = 1 -> GP x0.8); one release is -3%. Before 1930 there is no saturation at all, 1930-40 it is progressively switched on.
The same decay/half-life unit applies to the **boredom half-lives in 3c: they are in years**, not days (sets 3 years, stars 4 years, genre 2 years); earlier text calling the unit "presumably days" is superseded.

## 3f. Audience taste: the genre trend (decoded) **[code + data]**
`AudienceTaste` (singleton `AudienceTaste_GetInstance` `0x5202B0`; `AudienceTaste_Init` `0x523A60` loads `Data
ule	imeline.csv` through `AudienceTaste_LoadTimelineSeeds` `0x523090`) keeps, per genre, a list of dated events (0x28-byte entries: time at +0, value at +0x24). The CSV (`[timeline]` section) has one row per historical event: a date in decimal years and, in the genre columns, **1 = the event makes the genre popular, 0 = unpopular** (blank = no effect on that genre). Only the five columns `genre_action, genre_comedy, genre_horror, genre_romance, genre_sci-fi` exist; any other genre (e.g. thriller) never has events and is always **0.5**. (`[constants] halflife 4` is read; `spread 1` and `fullspread 1920` are stored but I did not find their use - presumably the lead time of the timeline's display or ticker.)
```
trend(genre, now) :
    e = the latest event of that genre with time <= now          // none yet -> 0.5
    dt = now - e.time                                            // in years
    trend = clamp01( 0.5 + (e.value - 0.5) * 2^(-dt / 4) )       // halflife 4 years
```
So each event kicks a genre to 1.0 (or 0.0) at the event date, and the **opinion drifts back to neutral 0.5 with a 4-year half-life**; only the most recent event counts (a new event replaces the previous one, even if it is a 0 right after a 1). The trend feeds `GP` (section 3) as `0.9 + 0.3*trend`: at most x1.2 right after a "1" event, x0.9 right after a "0", x1.05 when neutral. `AudienceTaste_GetMostPopularGenre` (`0x5217E0`) returns the genre with the highest trend (first wins ties).
Events per genre (year:value): 
* **action** 1924.5:1, 1927.7:0, 1931.4:0, 1934.3:1, 1953.3:1, 1955.4:1, 1961.2:1, 1965.2:1, 1979.2:1, 1983.2:1, 1990.6:0, 1995.4:1, 2007.4:0
* **comedy** 1927.7:0, 1929.8:1, 1931.4:1, 1939.7:1, 1945.3:0, 1987.8:1, 1995.4:0, 1999.9:1, 2003.2:1, 2012.4:1
* **horror** 1927.7:0, 1931.4:0, 1945.3:1, 1965.2:0, 1990.6:0, 1995.4:1, 2007.4:0, 2012.4:0
* **romance** 1927.7:0, 1931.4:1, 1934.3:1, 1955.4:1, 1972.4:0, 1981.5:1, 1995.4:0
* **sci-fi** 1927.7:1, 1939.7:0, 1950.4:1, 1957.8:1, 1961.2:1, 1969.5:1, 1975.4:1, 1979.2:1, 1981.5:0, 1983.2:1, 1995.4:0, 1999.9:1, 2012.4:1, 2015.4:1
(plus far-future sentinel rows at 2100.4 / 2150.4 that never trigger). The same file also carries `technology` and `opinion_smoking` columns used by other systems, and the event names (`timeline_WW2ENDS`, `timeline_MANONMOON`, ...) shown on the in-game timeline.

## 3b. Public interest in detail **[code; argument order of the call inferred]**
Two project fields feed it (both floats in 0..1):
* **Hype `h`** (`project+0x368`, accumulated PR). Every completed publicity action adds to it, clamped to [0,1]:
  * a **star press event** (`FUN_005b2880`, called from the PR room tick `FUN_0092a3a0` when the star's press session ends): `h += (clamp01(starRating*0.5) + 0.5) * starPrAdder` (x award-bonus-0 value when that bonus is active);
  * a plain **movie PR** (`FUN_005b2950`, called when the room reports `PR_COMPLETE` with no star): `h += moviePrAdder` (x award-bonus-0).
  The adders are globals `0xE544BC`/`0xE544C0` (compiled-in defaults 0.005/0.007; the `[pr]` section of releasing_movies.ini lists 0.15 / 0.1, presumably loaded over them - **unverified which values are live**). The PR room's progress bar (`HUD_PUBLICITY_PR_COMPLETE`) fills over `prtime` (60).
* **Release factor `D`** = the saved field **`PublicInterestMarketing`** (`project+0x36c`), set once when the movie is released (`CProject_FinalizeRelease`, `0x5B4F80`, which then builds the `GenrePopularitySnapshot` and runs `CProjectSuccess_Recompute`):
  `D = CProject_ComputePublicInterestMarketing(Qm, hypeCapped, level)` (`0x5B29E0`) with `hypeCapped = CProject_GetCappedHype = min(h, clamp01(Qm*0.5))` (**hype counts only up to half the quality**) and `level = project+0x370`.
  `base = 1 - Qm`; `D = base * {level 2: 0.25, 3: 0.5, 4: 0.75, 5: 1.0, 0 or 1: 0}`; with award bonus 0 active, `D` is nudged toward `clamp01(Qm - hypeCapped)` (`D -= (D - that) * 0.5`). Result clamped [0,1]. **So marketing spend gives a bonus that grows with how much room the movie has (low-quality movies benefit most) and is capped at `Qm/2` in the public-interest formula.**
* **Marketing level** = the saved field **`MarketingSpendLevel`** (`project+0x370`, an int enum; confirmed through the `CProject` save table `FUN_005BB460`, which lists `PublicInterestPR` / `PublicInterestMarketing` / `MarketingSpendLevel` consecutively at table offsets `+0x304/+0x308/+0x30C`, i.e. project `+0x368/+0x36C/+0x370` - the save table's base is `project+0x64`). Enum names (`FUN_00932230`, `MarketingLevel_GetName`): **0 `marketing_none`, 1 `marketing_lowest`, 2 `marketing_low`, 3 `marketing_medium`, 4 `marketing_high`, 5 `marketing_highest`**. It is written by `CProject_SetMarketingSpendLevel` (`0x5B0FE0`) from two drop handlers, both only when the project is in **phase 6 = post-production** (phase ids from the `CPhase*` constructors: 0 none, 2 writing, 3 design, 4 pre-production, 5 shoot, **6 post-production, 7 release**; `CProject_GetPhase`, project+0x228, vslot 0x24):
* **Marketing room** (`CMarketingRoom_OnProjectDropped`, `0x928260`): `level = room.level` (room+0x258). There are **five marketing room types** built by `RoomFactory_CreateInteriorObjectForName` (`CMarketingRoom` object size 0x25C, ctor `0x9281F0`, default level 2) whose names end in `minimal` (level 1), `low` (2), `med` (3), `high` (4) and `huge` (5) - the five tiers matching `SITT_ACTION_MARKETINGROOM_*`/`marketing_*`. Dropping a post-production movie on one of them sets the movie's level to that tier and posts event `0x80000B1F` for the project (= `MT_PROJECT_PHASEADVANCETORELEASE`, section 3h). Level 0 (`marketing_none`) is the default of a project that never visited a marketing room.
* **Release room** (`CReleaseRoom_OnProjectDropped`, `0x92EC70`): the release room (`releaseoffice`) builds, in `CReleaseRoom_CreateMarketingExplainers` (`0x92F190`, called when the room's interior is set up), **five `CMarketingExplainer` drop buttons**, one per room point index 0..4 of the room mesh (`FUN_009782d0` returns the point's position), named **`marketing_lev1` ... `marketing_lev5`** (loop index+1 -> constructor level argument; each is created disabled (`FUN_00931D40(expl, 0)`) and registered in the room's explainer list, `CMarketingExplainer_Constructor` `0x933CC0`; explainer object 0x224 bytes, level at +0x21C, name string at +0xB0 = `MarketingLevel_GetName(level)`; they are `CRoomPointExplainer` drop targets with the `UI_DROP_BUTTON_HIGHLIGHT` / `UI_ROOM_HIGHLIGHT` hover behaviour). Dropping a phase-6 movie on one of them sets `level = N` (`CMarketingExplainer_GetLevel`) and posts the same `0x80000B1F` event (3h); the global `DAT_01050594` is the drop target explainer. (The room also registers `SITT_ACTION_RELEASEROOM_RELEASE` and `..._NOPRAVAILABLE`.) A project already in phase 7 takes an earlier branch.
* **Marketing facility gating.** `DAT_0104ED6C` counts the existing **`CFacilityMarketing`** buildings (the lot facility `facility/facility_marketing`: ctor `0x849180` +1, dtor `0x8491E0` -1) and `DAT_0104ED68` counts those that are active (`CFacilityMarketing_UpdateActiveCount`, `0x848FF0`: facility state 4 or 5, i.e. built and not otherwise disabled). `CReleaseRoom_OnProjectDropped` only takes the explainer's level when **`DAT_0104ED68 > 0`** (at least one active marketing facility); the drop-tooltip predicate `CReleaseRoom_UpdateDropTooltip` at `0x92EFD0` (`param = dropped project`, phase 6 only) shows `SITT_ACTION_RELEASEROOM_NOPRAVAILABLE` when marketing facilities exist but none is active, otherwise `SITT_ACTION_RELEASEROOM_RELEASE`, and returns `(active count <= 0)`. So **without an active marketing facility the level stays 0 (no marketing spend, no `D` bonus)**; the five marketing room tiers (`minimal`...`huge`) are the facility's building tiers.
* **Accepting a drop** (`CMarketingExplainer_CanAcceptDrop`, `0x9326C0`, `CMarketingExplainer` vslot 31): rejects the drop if the room's facility object (`room+0x1D0 -> +0x24C`) is **in disrepair** (`CFacility_IsInDisrepair`, `0x5281A0` = byte `facility+0x2E4`, the `vslot 0xC4` test also used by `CFacilityMarketing_UpdateActiveCount`); otherwise accepts only a `TMMobile/CProjectObject` whose project is in phase 6. (`0x9322B0` likewise returns false when the facility is in disrepair; not a Ghidra function.)
* **What "active" means for a marketing facility**: `CFacilityMarketing_UpdateActiveCount` counts a facility when its state (`facility+0x2B8`) is **4 or 5** and it is **not in disrepair**. State 5 is the fully built/operating state (the facility's glow/highlight is shown only for state 5, `CFacility_UpdateVisualsAndRunningCosts`, `0x845870`); state 4 is the preceding state (not named; likely just completed/ready). Facility condition (`facility+0x2C4`) dropping below **0.1** raises `TANNOY_DISREPAIR_WARNING_FACILITY` once (flag `+0x2E5`, re-armed when condition recovers); that the disrepair byte `+0x2E4` is what that same drop sets was not traced. So a **neglected (broken-down) marketing facility disables marketing spend** until repaired.
Reset to 0 by the project constructor (`0x5C12F7`). So **the marketing tier is chosen by which marketing room the player drags the finished movie through before release** (the last one visited wins), and it only acts through `D` (section above).

`ComputePublicInterestFactor(D, hypeCapped, Qm)`:
```
D' = min(D, clamp01(Qm * 0.5))          // both inputs capped at half the quality
s  = clamp01(D' + hypeCapped)           // total publicity, never above Qm
cover = (Qm == 0) ? 0
      : (s <= Qm) ? 1 - clamp01(Qm - s) / Qm            // = s / Qm
      : 1 - clamp01(s - Qm)^3                           // over-publicity: cubic penalty (exponent 3.0 at 0xD1BA70)
imbalance = |clamp01(hypeCapped - D')| / clamp01(hypeCapped + D')   // 0 if s == 0
F = (1 - public_interest_ratio(0.3) * imbalance) * cover
PI = 1.0 + (1.4 - 1.0) * F
```
So the best public interest needs `s` to reach the movie's quality (hype and D each worth up to Qm/2) **in balance** (up to -30% of F when only one of the two is present). Typical: Qm=0.6, hype 0.3, D' 0.3 -> s = 0.6, cover 1, imbalance 0 -> PI = 1.4. No PR at all but a low-quality movie (D = 0.4*0.5... only if mode>=2) gives a little. **[Argument order a=D, b=hype, c=Qm inferred from the caps; the decompiler's parameter naming of the call is unreliable.]**
For **AI projects** see section 5 (their public interest is `1.0 + 0.12 * F` with the over-publicity penalty).

## 3d. Era fit and technology: loaded or saved, but not used **[code]**
* **Era fit does not exist in the executable's tuning loader.** The strings `era_fit_min`, `era_fit_max`, `set_era_fit_cutoff` are absent from `MoviesSE.exe` (no string containing "era_fit" / "cutoff"), so those lines in `releasing_movies.ini` are **never read**. `ReleaseCalc_LoadTuningData` (`0x5DF000`) loads only: public_interest min/max/ratio, star_ratings_of_cast min/max/proportion, technology min/max, genre_popularity min/max, the three `success_overall_*`, the four `*_boredom_bound`, `technology_pioneering_bonus`.
* `CProjectSuccess` does have saved slots named **`EraFit`** (+0x64) and **`Technology`** (+0x6C) next to `Overall`, `PublicInterest`, `CastStarRatings`, `WeightedBoredoms`, `Unweighted*Boredom` (`CProjectSuccess_RegisterSaveFields`, `0x5DDDB0`) - leftovers of an earlier design where the success multiplied in an era-fit and a technology factor. `CProjectSuccess_Recompute` never reads or writes them: the product is exactly `TP * SR * GP * BO * PI` (section 2).
* `technology_min`/`technology_max` (0.7 / 1.0) are written to globals `E54C0C`/`E54C10`, which have no readers.
* The only "era" logic found is in the **movie title generator** (`FUN_005BE730`): the current year selects the title word list (`ERA_PRE_30S` < 1940, `ERA_40S_50S` < 1960, `ERA_60S_70S` up to 1979+, `ERA_POST_80S`, plus `ERA_TIMELESS`) and the genre selects `GENRE_*` lists - purely cosmetic naming.
So in this build **a movie's release date and the technology level do not affect its box office** apart from the pioneering bonus (section 3, 1.1x). Similarly `[genre_fit] max_from_ideal` and `pre_production` are read only by `QualityCalc_LoadTuningData` (quality side).

## 3g. Marketing cost and the release sequence **[code + data]**
* **Cost per level** (`Data\misc_costs.ini [project]`, loaded by `MiscCosts_LoadTuningData` `0x5CADC0` into a level->money map `DAT_0104D6D4`, read by `MarketingSpend_GetCost` `0x5C8B90`): level 0 (none) **$0**, 1 `marketing_spend_lowest` **$0**, 2 `low` **$50,000**, 3 `medium` **$100,000**, 4 `high` **$150,000**, 5 `highest` **$200,000**. Level 1 therefore costs nothing and gives no benefit (same as none); each step above adds $50k and +0.25 of the `(1 - Qm)` release-factor weight.
* **Charging**: `CPhaseRelease_StartRelease` (`0x5AF7C0`, the function that advances a movie into the release phase) performs, in this order: create the release phase, play `UI_CASH_SOUNDS`, set the release date (`FUN_005B0E90`), **`CPhaseRelease_ChargeMarketingSpend`** (`0x5C8C40`: adds `MarketingSpend_GetCost(project.level)` to the project's cost total (+0x70/+0x74 of the costs object) and deducts it from the player studio as expense category 6 = marketing), **`CProject_FinalizeRelease`** (computes `D`, builds the success snapshot - sections 2/3b), **`CProjectIncome_CreateForPlayerProject`** (the revenue pool, section 4), `FUN_005AE9C0`, **`Release_PushGenreSaturationEntry`** (adds set/star boredom and genre saturation - *after* the success has been computed, so a movie is never penalised by its own release), studio movies-released counter (`studio+0x1E4`)++, `CProject_RecordLeagueTableEntry` (movie star rating, section 3i), then award/archive bookkeeping. `CProject_GetMarketingCostText` (`0x54BD20`) formats the same cost for the UI.
* So the marketing decision is: pay $0/50k/100k/150k/200k to raise `D` from 0 to `0.25/0.5/0.75/1.0 x (1 - Qm)`, which only counts up to `Qm/2` (together with PR hype, section 3b). Because `D` is capped at `Qm/2` (before the hype is added), a tier stops adding anything once `m * (1 - Qm) >= Qm/2`, i.e. `m >= Qm / (2 (1 - Qm))`: for `Qm = 0.4` that is `m >= 0.33` (so 'medium' already saturates), `Qm = 0.5` -> `m >= 0.5` ('medium'), `Qm = 0.6` -> `m >= 0.75` ('high'), `Qm = 0.8` -> `m >= 2` (never: even 'highest' still helps). Spending above the saturating tier is wasted for the `D` term (hype from PR is independent).

## 3h. Event 0x80000B1F = "advance the project to the release phase" **[code]**
`MovieProjectSystem_Constructor` (`0x5C4970`) registers the project message names with `FUN_00471840(name, id)`; the ids (`0x80000000 + n`): `MT_PROJECT_PHASEDESIGN 0x80000A2F`, `PHASEMANAGE 0x80000A57`, `PHASEADVANCETODESIGN 0x80000A7F`, `PHASEADVANCETOPREPRODUCTION 0x80000AA7`, `PHASEADVANCETOSHOOT 0x80000ACF`, `PHASEADVANCETOPOSTPRODUCTION 0x80000AF7`, **`PHASEADVANCETORELEASE 0x80000B1F`**, `RANDOMTITLE 0x80000B47`. The same constructor also loads `[pr]` from `releasing_movies.ini` into the live PR adders (`star_pr_public_interest_adder` -> `0xE544BC`, `movie_pr_public_interest_adder` -> `0xE544C0`, `prtime` -> `FUN_00929120`), so **the live values are the ini ones: 0.15 for star PR and 0.1 for movie PR** (the 0.005/0.007 seen in the executable are only the pre-load defaults), plus `starratingboxoffice`/`starratingquality`/`starratingawards` from `global.ini [project]` (`0xE544C4/C8/CC`, the star-rating weights).
The marketing room and release room drop handlers post the event with `EventManager_PostEvent` (`0x470A70`, `DAT_0104917c`; source = the project). The receiver is `CProject_OnEvent` (`0x5BEF00`, the project's event handler, vtable at `0xD2A15C`). For each `PHASEADVANCETO<X>` message it walks the phase chain starting at the current phase (`project+0x228`) and **calls each phase's `Advance()` (vslot 5 = vtable offset 0x14) until it reaches the phase id it wants** (id 7 for release, 6 post-production, 5 shoot, 4 pre-production, 3 design). If that phase is not the current one it replaces the current phase (the old one is released, `FUN_005B12A0(project+0x214, newPhase)`). For release the step from post-production is `CPhasePostProduction_AdvanceToRelease` (`0x5AAC50`), which stores the director/record into the project and calls **`CPhaseRelease_StartRelease`** - so **the marketing/release room drop is what actually releases the movie**: level set first, then the event triggers the charge, `CProject_FinalizeRelease`, income and saturation (section 3g). After the advance (or if already released) the handler opens the release results screen (`ReleaseScreen_GetOrCreate(project, 1)`, `0x6F6410`, singleton `DAT_0104DD70`, closed by `MT_RELEASE_CLOSESCREEN`) and runs the objectives/tutorial check `FUN_0085F5C0(project)`.

**The movie's star rating** (`+0x170`, saved as `StarRating`; shown as stars on the main page, `RELEASE_FINAL_RATING`, and stored in the league table): `CProject_ComputeMovieStarRating` (`0x5B8C90`, called once from `CPhaseRelease_StartRelease` through `CProject_RecordLeagueTableEntry` `0x5B9050`, which also creates the `PLeagueTableEntry`):
```
r = clamp01( 0.73 * clamp01(S) )                     // starratingboxoffice  (global.ini [project]; S = success, clamped to 1 here)
r = clamp01( r + 0.33 * Qm )                         // starratingquality
r = clamp01( r + 0.00 * awardsFlag )                 // starratingawards = 0 (flag = movie has any award, CProject_GetAwardsRatingFlag)
```
(stored into the income record too, `FUN_005CE430`, +0xB8). So **the displayed rating is mostly box office (success) with quality as a secondary term; success above 1.0 is cut off in the rating (although it still raises revenue)** and a movie with `S = 1` and `Qm >= 0.82` already reaches 1.0.
The AI studios use the same weights through `FUN_005A3CA0` / `FUN_005A4060` (a 0.5, 0.25, ... weighted series over their stars' contributions).

### 3l. Pioneer technology window (decoded + validated against the RESEARCH log) **[code + measured]**
`CStudioPlayer_HasActivePioneerTechnology(date)` (0x518D00) walks the research item list and returns true if **any** item satisfies: `item+0xA0 == category of "moviemaking"` (category id 0 in the log; the log shows categories 0..3 and only 0 counts), `item+0x10B == 0` (item is part of the tree / not locked), `item+0x134 <= date` and `date < item+0xA4`. Meaning of the two dates (float game-days, shown as years in the log): **`+0xA4` is the technology's natural availability date** (fixed, e.g. 1940.129, 1944.091); **`+0x134` is the effective date, which starts equal to `+0xA4` and is pulled earlier while the player researches it** (it drops continuously, about 5 game-years per real game-year of research, e.g. 1942.64 -> 1942.19 -> 1941.73 over three months). As soon as the effective date passes the current date the technology is usable *before its time* and the movie gets **TP = 1.1** until the natural date arrives; after that the bonus ends unless another moviemaking technology is ahead of its time. Validation: TP was 1.0 at 1930.02 and 1.1 at 1931.75 (item with `+0x134` = 1930.525, `+0xA4` = 1934.052), 1.1 at 1934.01 (same item), 1.1 at 1934.99 .. 1939.80 (item `+0x134` = 1934.729, `+0xA4` = 1940.129), and 1.0 for the 1927-1930 releases. Correction after the user reported being ahead in research: a second moviemaking item (`0x1D343458`, natural date 1944.0905) reached its effective date at 1936.25, so the bonus runs until **1944.09** (the latest natural date among finished items), not 1940.13. The user's 'technology that unlocks in 1961' does not match any logged moviemaking natural date (nearest 1954.09 / 1964.10) - needs the technology's name or the next research log to identify; RESEARCH changes are only logged when an item changes, and no category-0 item changed after 1936.33. Practical rule: research a moviemaking technology early (the earlier you finish it relative to its `+0xA4` date, the longer the 10% success bonus lasts).

### 3k-4. 1945 ceremony and the first PR-marketed release (measured) **[measured]**

### 3m. AI studio release decision (decoded from `CStudioAI_DecideAndReleaseMovie` 0x5154A0 and `AIStudios_LoadRuleCsv`) **[code, not yet validated against the log]**
Globals loaded from `Data/rule/aistudios.csv` (renamed in Ghidra as `AIRule_*`): Appearing variance 2 -> `0x104BD2C`; Movie release desire threshold 0.5 -> `0x104BD88`; Success target range width 0.5 -> `0x104BD8C`; Difference target 0.1 -> `0x104BD90`; Deviation target 0.2 -> `0x104BD94`; Difference multiplier 3 -> `0x104BD74`; Deviation multiplier 12 -> `0x104BD78`; Minimum time between releases 0.5 y -> `0x104BD98`; Maximum time between releases 2 y -> `0x104BD9C`; Time between desertions 2 y -> `0x104BDA0`; rival experience gain constant 0.1 / multiplier 0.5 -> `0x104BD80` / `0x104BD7C`; research probability curve 0.03..0.75 -> list `0xF87A64`.
Per AI studio, each tick (`CStudioAI_Tick` -> decide):
```
successDiff = CStudioAI_ComputeSuccessDifference(studio)        // stored at studio+0x298 (logged as successDiff)
mean, rms   = mean and RMS of that value over all AI studios
desire      = clamp01( (DifferenceTarget - mean) * 3  +  (DeviationTarget - rms) * 12 * successDiff )
elapsed     = now - lastReleaseTime(studio+0x168) - MinTime         // years since last release minus 0.5
half        = (MaxTime - MinTime) * 0.5 = 0.75 y
score       = elapsed < half ? desire * elapsed/half               // ramps 0 -> desire
                             : desire + (1-desire) * (elapsed-half)/half   // then desire -> 1
if score > 0.5: CStudioAI_MakeMovie(studio)                    // release a movie
while AI_ExtraReleaseAccumulator > 0.5: MakeMovie; accumulator -= 1   // extra releases, accumulator fed elsewhere
```
So an AI studio never releases before 0.5 years after its last film and always has score 1 by 2.5 years; with desire d the score passes the 0.5 threshold at `elapsed = 0.75*0.5/d` (before the midpoint, only if d > 0.5) or `0.75*(1 + (0.5-d)/(1-d))` after it. Low `desire` (the studios are already close to the target mean/deviation) lengthens the gap up to 2.5 years; a high one releases every ~1 year. `CStudioAI_MakeMovie` (0x515290): script quality = `AIStudioScriptParams_RollScriptQuality`, genre = `CStudioAI_ChooseGenre`, hype = clamp01(`PRLevel(+0x288)` + rand(-var, +var) with var = `PRVar(+0x28C)`), then `AIMovie_CreateSuccess`, `Release_PushGenreSaturationEntry_AI`, `AIMovie_CreateIncome`.

### 3p. Stunt shots: success roll, injuries and performance (decoded; stunts unlock around 1960) **[code + `Data/stunts.ini`]**
**Success roll** (`ShootController_RollStuntOutcome` 0x4EA1D0, config in `stunts.ini [successfailure]`, globals renamed `Stunt_*`). For every performer of the shot (the stunt double if there is one, otherwise the actor):
```
ability  = ((maxhealthability - minhealthability) * health + minhealthability)      // 1.0, 0.5 -> 0.5 + 0.5*health
ability *= (health < healththreshold(0.01)) ? stuntabilityinjurymodifier(0.7) : 1   // badly injured performers
performer score = ability * traits["Stunts"]                                        // clamped 0..1
shot score      = mean of the performers' scores          (stored at shoot controller +0xF8; the release screen's "take score")
diff            = shot score - StuntState difficulty      (scene difficulty, 0.4/0.6/1.0 style values)
chance          = diff >= 0 ? 0.80 + (1.10 - 0.80) * diff : 0.80 - (-0.40 - 0.80) * diff     // = 0.80 + 0.3*diff  or  0.80 + 1.2*diff
if Lucky Charm (bonus 14) active: chance += luckycharmbonus (0.10)
chance = clamp(chance, stuntchancemin 0.05, stuntchancemax 0.98)
success = rand01 < chance   -> channel "ai_stunt_fail" = !success
```
So at equal skill and difficulty a stunt succeeds 80% of the time; being 0.1 above the difficulty gives 83%, 0.1 below gives 68%, and the chance is bounded to 5..98%. Lucky Charm adds a flat 10 points. **Injuries** (`ShootController_ApplyStuntConsequences` 0x4E2240, `[injuries]`): per performer `k = clamp01(difficulty - 0.3 * Stunts)` and health loss = `lerp(min, max, k)` with failure 0.1..0.8 and success 0.1..0.2 (so even a perfect success costs 10% health, a failed hard stunt by an unskilled performer 80%); `TANNOY_STUNT_SCENE_SUCCESS/FAILURE` is announced. **Quality contribution** (`QualityCalc_StuntPerformance`): `skillFactor * healthFactor * likenessFactor * levelFactor * successFactor` where `skillFactor = skillmin + (skillmax-skillmin)*Stunts` (0.9..1.1 from `[performance]`), `levelFactor = stuntlevelminimum + (max-min)*difficulty` (0.9..1.4), and `successFactor` is the success multiplier (0.8 failed, 1.25 succeeded - mapping of the table constants to `[performance]` keys is by order and not verified); likeness 0.9..1.0 (x1.1 `likenessbonus` for a double that looks like the actor), health 0.9..1.1 with `injurymultiplier` 0.9. Experience for stunt performers: `stuntxpsuccessmin/max` 0.02..0.06, failure 0.01..0.04 (`[experience]`), applied by `CStaff_AddStuntExperience`. The tracker's `REL_PLAYER_BARS` line (`meanStuntTake`, `stuntCount`) will give the actual shot scores once stunts exist.

### 3q. Building condition and disrepair (decoded) **[code]**
Every building/set asset (`CAsset`, base class; facilities derive from it) has a condition float at `+0x2C4` (starts at 1.0 in `CAsset_Constructor`), a lifespan duration at `+0x2C8` and a decay start date at `+0x2CC`. `CAsset_UpdateConditionAndDisrepair` (0x5343D0, runs each update): if the tutorial/cheat object (`DAT_0104A974+0x68`) is set, condition is pinned to 1.0 and disrepair is cleared. Otherwise, once the decay date has passed, condition falls by `(1/dayLength)/lifespan` per update, i.e. **linearly from 1.0 to 0 over its lifespan**; when it reaches 1.0 again the `task_repairman` job is cleared. **Disrepair has hysteresis:** the flag at `+0x2E4` (`CFacility_IsInDisrepair`) is set when condition `<= 0.05`, records the date at `+0x2E8`, posts `TANNOY_BUILDINGS_IN_DISREPAIR` and starts spark effects; it is cleared only when condition `>= 0.95`. Separately `CFacility_UpdateVisualsAndRunningCosts` posts `TANNOY_DISREPAIR_WARNING_FACILITY` once when a facility's condition drops to `<= 0.10` (flag `+0x2E5`, re-armed above 0.10). `CAsset_ClearDisrepairState` (0x527FD0) resets the timer, the disrepair flag and the warning flag. A facility that is in disrepair counts as unavailable (`0x4CA9F0` returns "blocked" if `IsInDisrepair` or the flag at `+0x55C`), and the marketing facility keeps a global working-count (`DAT_0104ED68`) that is decremented when a facility that is not in disrepair is destroyed. Practical effect: a building is fully usable until condition 0.05 and unusable from then until a repairman (task `task_repairman`) restores it above 0.95, so repair crews must be sent well before a building reaches the low warning at 0.10. The asset state at `+0x2B8` is decoded by `CAsset_UpdateStateMachine` (0x5347F0): **0** idle; **1** placed, waiting for a builder (set by `CAsset_OnPlaced` when the building has construction work, `+0x2DC` > 0; at the ready time `+0x3B4` it moves to 2); **2** under construction (the `task_builder` job is active until the building work is done); **3** being demolished (`CAsset_BeginDemolish`, removes the asset when its timer expires); **4** placed with no construction work (instant build: when the timer expires it finishes and copies the work value); **5** operational (`CAsset_SetOperational`; the default in the constructor): in state 5 the builder task is switched off, the condition update of 3q runs, and if the building is in disrepair the `heal`/repair task is activated. So states 1-2 are the 'being built' stages that `buildingwork` in the facility ini controls, 3 is demolition and 5 is the normal working state.

### 3v. Marketing "D" and the public-interest balance (corrected, decoded + validated) **[code + measured]**
`CProject_FinalizeRelease` (0x5B4F80) stores `D = CProject_ComputePublicInterestMarketing(...)` into `project+0x36C` at release, using the *capped hype* `hc = min(hype, Qm/2)` and the marketing level (`+0x370`): `D = (1 - hc) * m[level]` with `m = {1: 0, 2: 0.25, 3: 0.5, 4: 0.75, 5: 1.0}` (jump table at 0x5B2B58; anything else gives 0), then clamped to 0..1; the On The Radar bonus (flag 0) modifies it further. Verified exactly on all three PR releases: level 3, hype 0.3082 -> D = 0.6918*0.5 = 0.3459; level 4, hc 0.2989 -> D = 0.7011*0.75 = 0.5258; level 5, hc 0.3104 -> D = 0.6896. **Correction to 3b:** D is *not* capped at Qm/2 (only the hype is capped); the earlier release had D below the cap by chance. The public interest then is `s = clamp01(D + hc)`, `imbalance = |hc - D| / (hc + D)`, `cover = s <= Qm ? s/Qm : 1 - (s - Qm)^3`, `F = (1 - 0.3*imbalance) * cover`, `PI = 1 + 0.4*F` - verified on both new releases: Qm 0.6208, hc 0.3104, D 0.6896 -> s = 1.0, imbalance 0.379, cover 0.9455, F 0.838, **PI 1.3352 (logged 1.3352)**; Qm 0.5978, hc 0.2989, D 0.5258 -> s 0.8247, imbalance 0.275, cover 0.9883, F 0.907, **PI 1.3627 (logged 1.3627)**.
**Practical consequence: level 5 is not the best level.** Since the hype is capped at Qm/2 and D = (1 - hc) * m, level 5 always gives `D = 1 - hc >= 0.5`, far more than `hc <= 0.31..0.5`, which wastes interest on imbalance and over-publicity. For Qm 0.62 with full hype (hc 0.31): level 2 -> PI 1.284, **level 3 -> PI 1.394**, level 4 -> 1.364, level 5 -> 1.335. Level 3 (D close to hc) is best when the hype is near its cap and is cheaper than 4 or 5; with little hype it shifts: for hc 0.1 and Qm 0.62, F is 0.46 (level 2), 0.72 (level 3), **0.77 (level 4)** and 0.72 (level 5), so level 4 wins there. Rule of thumb: pick the level that maximises F = (1 - 0.3*imbalance)*cover for your hc; roughly, the more hype, the lower the level.

### 3w. Marketing cost versus return **[config + code + model]**
`MarketingSpend_GetCost` looks the level up in a table loaded from `Data/misc_costs.ini [project]` (`marketing_spend_lowest/low/medium/high/highest` = **$0 / $50,000 / $100,000 / $150,000 / $200,000** for levels 1-5); `CPhaseRelease_ChargeMarketingSpend` charges it once, when the movie is released, to the player studio (finance category 6). The whole revenue pool is eventually paid out: in the log every finished movie's payouts sum to 100% of its initial pool within about 800 game days (the daily percentage only sets the timing), so the box-office total is the pool `1.4M*S^2 + 70,000` and the value of marketing is the pool increase from the higher public interest. Model for a typical film (TP 1.1, SR 0.94, GP 1.07, BO 0.93) with the PI of 3v, pool gain minus cost per level (L1 = no marketing):
| film | L2 | L3 | L4 | L5 |
|---|---|---|---|---|
| Qm 0.62, hype cap 0.31 (full hype) | +100k | **+148k** | +77k | -3k |
| Qm 0.62, hc 0.20 | +134k | **+169k** | +109k | +32k |
| Qm 0.62, hc 0.10 | +113k | **+166k** | +137k | +67k |
| Qm 0.75, hc 0.375 | +90k | **+162k** | +145k | +70k |
| Qm 0.75, hc 0.15 | +130k | +182k | **+201k** | +136k |
| Qm 0.50, hc 0.25 | **+114k** | +91k | +19k | -67k |
So marketing always pays back (every level 2-4 returns 2-5x its cost), **level 3 ($100k) is the best choice for most films, level 4 only for higher-quality films with little hype, level 5 ($200k) is never the best and loses money for full-hype films, and for low-quality films (Qm about 0.5) level 2 ($50k) is best.** Level 1 only makes sense when you cannot afford the spend. These are model predictions from the validated formulas, not measured outcomes.

### 3x. How hype is generated (publicity room) **[code + config]**
Hype is the float at `project+0x368`; the only writers are the two functions called from `PublicityRoom_Tick` (0x92A3A0) when a session in the publicity office finishes. Config: `releasing_movies.ini [pr]` -> `star_pr_public_interest_adder = 0.15`, `movie_pr_public_interest_adder = 0.1`, `prtime = 60` (the session length, loaded by `MovieProjectSystem_Constructor` into `0xE544BC / 0xE544C0`). **Star press session** (`CProject_AddStarPressHype(project, starRating)`): `hype += (clamp01(0.5 * starRating) + 0.5) * 0.15`, i.e. **0.075 for a star rated 0 up to 0.15 for a star rated 1** (a star rated 0.6 adds 0.12, 0.8 adds 0.135), clamped to 1.0. **Movie PR session** (`CProject_AddMoviePRHype`): `hype += 0.10`. If the On The Radar award bonus (flag 0, `public_awareness_boost` 2) is active both additions are doubled. The room runs one session at a time per star or project: a flag (`+0x98`) makes each completed session add its hype once, then the star/project leaves, and a "PR_COMPLETE" tannoy is shown. Because only `min(hype, Qm/2)` counts (3b, 3v), the useful amount is small: a Qm 0.62 film needs 0.31 hype (two movie PR sessions plus one star session, about three sessions in total), a Qm 0.8 film 0.40, a Qm 0.5 film 0.25; hype beyond the cap is wasted (the log's raw hype values 0.53 and 0.74 on the last two releases were well above their caps of 0.31 and 0.30). The room costs nothing per day (`daily_movie_pr_room_fee`, `daily_star_pr_room_fee` = 0 in `misc_costs.ini`), so the only price of hype is the time the stars and project spend there. Not yet checked: whether hype decays with time, and whether the same star can do repeated sessions on one project.

### 3y. Repair work and the star grudge system (decoded from `DesireTaskRepairman_*` and `global.ini`) **[code + config]**
A repair job is a `task_repairman` desire (`DesireTaskRepairman_Constructor`, 0x840FD0) given to a staff member or star by the building's `heal` task (3q). While it runs, `DesireTaskRepairman_UpdateProgress` feeds the asset activity's progress to the animation channel `ai_progress`; on completion the worker gains Lot experience (`LOT_PERHAMMERREPAIR` 0.0003 per hammer blow in `experience.ini`; each blow does `repairworkperhammermin/max` = 0.5..1.5 work units, and a building's `repairwork` (5..50 units, 3r) is the total needed). **If the worker is a star, giving them repair work creates a grudge:** the constructor calls `CGrudges_AddOrRefreshGrudge` with `[star] dislikestaffjob = -0.4` and recovery `forgivestaffjob = 0.0002` (key `grudge_staff_job`) - so stars should never be sent to repair or build. Other grudge parameters in `global.ini [star]` (dislike / recovery per tick): pay cut -0.5 / 0.0001, worse trailer -0.3 / 0.0001, paparazzi photo -0.5 / 0.0001, actor-director swap -0.3 / 0.0001, being fired -0.1 / 0.0001, photo of sex -0.3, photo at detox -0.1, unfulfilled desires -0.5 (staff) / 0.0001, being grabbed (dragged) 0.1 (staff) or 0.75 x ego (stars); positive feelings: pay rise +0.5 (forgetting -0.0001), release a movie +0.3 (-0.00025), hire 0.0 (-0.000417), award +0.1 (-0.000008), feeding an addiction +0.3 (-0.00025), auction win +0.25 / lose -0.25, being given an assistant +0.15. ### 3z. What star mood does (decoded) **[code + `mood.ini` + `releasing_movies.ini`]**
**Effect on films:** `CStar_GetMoodPerformanceFactor` (0x5D79A0), called by `QualityCalc_ActorPerformance`, turns the star's mood `m` (0..1) into an acting multiplier between `star_mood_min` 0.8 and `star_mood_max` 1.2 (`releasing_movies.ini [min_max]`): `factor = 0.8 + 0.4*f`, where `f` is a stepped curve in three bands set by the cast effect's **lower and upper mood thresholds** (`CProjectCastEffect_GetEffective{Lower,Upper}MoodThreshold`; the Easy To Please award bonus caps them at **lower 0.15 and upper 0.75**, `lower_mood_val`/`upper_mood_val`): below the lower threshold `f` rises from 0 over the low band (factor 0.8 up to about 0.9), between the thresholds it is a flat middle value (`f` = 0.5, factor 1.0), and above the upper threshold it climbs through the top band toward 1.0 (factor about 1.1 up to 1.2). The band widths come from `star_mood_step` (0.25 in the ini) held in a runtime global (`0x104D7CC`) that I have not yet read from a running game, so the exact band edges (0.8-0.9 / 1.0 / 1.1-1.2) are the expected values, not measured. In plain terms: **a star in a good mood (above the upper threshold) acts up to 20% better, an unhappy star (below the lower threshold) up to 20% worse, anything in between is neutral; Easy To Please lowers the bar so that the penalty zone (mood under 0.15) is smaller and a mood above 0.75 already earns the bonus.**
**What moves mood** (per-tick stress / boredom deltas, `Data/mood.ini`): working on a movie +0.00006 / -0.0004 (so a working star gets more stressed but less bored); rehearsing +0.00006 / -0.0002; stunt training +0.00006 / -0.0002; waiting on a movie +0.00003 / 0; doing PR +0.00002 / -0.0004; make-over +0.00002 / 0; health clinic +0.0002 / -0.0002; **staff jobs +0.0002 / +0.0002 (the worst activity: both go up)**; restaurant -0.0003 / -0.0003; snack van -0.00015 / -0.00015; drinking -0.0003 / -0.0003; eating or drinking on the spot -0.0002 / -0.0002; idling -0.000008 / +0.00004; trailer (alone or together) -0.00008 / 0; detox 0 / -0.0002; hospital +0.00004 / +0.00004. Health also feeds mood (`MOODHEALTHINJURY` -0.2, range -0.4..0), and `MAXIMUMBOREDOMONPROJECT` caps boredom from one project at 0.19. Practical rule: stress builds slowly while stars work and falls fastest with restaurants and drinking (-0.0003) and in the trailer (-0.00008); boredom is relieved by working, so a star who is kept busy is rarely bored, and a star left idle slowly gets bored (+0.00004). The mood HUD behaviour of `CStar_ChooseNextActivityByMood` (0x58F440) switches the star to complaining/idle animations when the mood value crosses two thresholds (`0xD26EAC`, `0xD26EB0`).

## 4. Box-office revenue **[code + data]**
When a movie is released the game creates a **`CProjectIncome`** record (`CProjectIncome_CreateForPlayerProject` `FUN_005cdb80`; AI studios use `CProjectIncome_CreateForAIProject` `FUN_005cdd90`; class RTTI `TM::CProjectIncome`, size 0xE8). Money is a **64-bit fixed-point** value with 23 fractional bits.
```
S           = CProjectSuccess.+0x90                          // FUN_005dcf80 reads it
total       = (revenue_multiplier * S^2 + revenue_base)      // 1,400,000 * S^2 + 70,000     -> income.Pool (+0x90) and InitialPool (+0x98)
piFactor    = (1 - pi_effect) + pi_effect * clamp01( movie.interest(+0x36c) + movie.pr(+0x368 capped) )     // pi_effect = 0.6
AdderMax    = total * adder_percentage                       // 0.0005 -> +0xA0   ("AdderMaximum")
DailyPct    = base_percentage * piFactor                     // 0.013 * piFactor -> +0xA8 ("DailyPercentage")
DailyMul    = 1 + increase_percentage * piFactor             // 1 - 0.004*piFactor -> +0xAC ("DailyPercentageMultiplier")
```
The save-game field names of the record (`RegisterSaveFields`, `FUN_005cd140`) confirm the model: `Pool`, `InitialPool`, `AdderMaximum`, `DailyPercentage`, `DailyPercentageMultiplier`, `GL_TANNOY_TRIGGERED`, `DayOfTannoyAnnouncement`, `PRecipient` (the studio), `PProjectObject`.
So: **expected total revenue** = 70,000 + 1,400,000 x S^2 (e.g. S = 0.5 -> 420,000; S = 1.0 -> 1,470,000; S = 1.4 -> 2,814,000). Each day a fraction `DailyPercentage` of the pool is paid out, and that fraction is multiplied by `DailyMul` every day (< 1 with the shipped values, so earnings decay; high public interest (`piFactor` near 1) makes both the start rate larger (up to 0.013) and the decay faster (0.4%/day)).
### 4b. The daily payout tick (`CProjectIncome` vtable slot 3, `0x5CCE10`) **[code, partly inferred: x87 temporaries are lost in the decompile]**
Per game-day tick while `Pool` (+0x90) is non-zero:
```
payout = Pool * DailyPercentage  (+0xA8)  +  rand(0 .. AdderMaximum (+0xA0))      // rand = FUN_00990e30(0, adder)
if payout >= Pool: payout = Pool                                                   // last day pays out the remainder
PRecipient.AddMoney(payout)           // vtable +0x28 of the studio at +0xC4; also pops a floating "+$" text on the project object (+0xE4)
Pool -= payout
DailyPercentage *= DailyPercentageMultiplier (+0xAC)                              // rate decays each day
```
When `Pool` hits 0 the record sets the archive timer (`+0xC8 = now + _DAT_00e54848`) and, once, fires the Tannoy **`TANNOY_RELEASED_TIMETOARCHIVE`** (flag +0xCC). `0x5CDA30` / `0x5CE3E0` are the (thunk and real) scalar deleting destructor of `CProjectIncome`, not part of the payout.

## 5. AI studio movies **[code + data]**
Rival studios (`CStudioAI`, from `Data
uleistudios.csv`) make "AI movies" that are scored by the **same** `CProjectSuccess_Recompute` (with `project == null`, record at `+0x8C`) and paid by the same `CProjectIncome` model. Differences:
* **Quality `Qm` = script quality only.** `CStudioAI_MakeMovie` (`0x515290`) rolls `AIStudioScriptParams_RollScriptQuality` (`0x5A1F10`): with `t = clamp01((year - 1900) / 100)`, `mean = lerp(script quality 1900, script quality 2000, t)`, `spread = lerp(script variation 1900, script variation 2000, t)` (csv rows `Script quality/variation 1900/2000`, stored at params +0x60/+0x64/+0x68/+0x6C; mapping by csv order), then **`q = clamp01(mean + (rand01 * spread - spread/2))`** - uniform noise of +-spread/2. No cast, crew, set or relationship factors. Stored as the movie's quality (`AIMovie_SetQuality`, +0x110, also +0x114).
* **Hype** (`AIMovie_SetHype`, +0x118) = `clamp01(studio.base + uniform(-var, +var))` from the studio fields at `+0x288/+0x28C` (the csv `Marketing` and `Marketing variance`; mapping by name, not traced).
* **Public interest `PI`** (`CProjectSuccess_ComputePublicInterestFactorAI`, `0x5DD2D0`): `h = hype, q = quality`; `cover = (h <= q) ? h / q : 1 - clamp01(h - q)^3`, `PI = 1.0 + (1.4 - 1.0) * 0.3 * cover` = **1.0 .. 1.12**. (Unlike the player, AI hype is not capped by quality, so over-hyped AI movies are penalised.)
* **Star ratings `SR`**: the movie's stars (+ director if a star) via `CollectCastStarRatingsSortedAI`, quality `q = record+0x110`, same formula as the player's.
* **Genre `GP`, boredom `BO`**: fixed **1.0** (`+0x9C`, `+0xA0`) - AI movies are not affected by genre trend or boredom, and the set boredom report value `+0xA8` is 0.5.
* **Tech pioneering `TP`**: uses the studio's own tech check (record+0x154) instead of the player's.
* **Revenue**: `CProjectIncome_CreateForAIProject` (`0x5CDD90`): same pool `revenue_base + revenue_multiplier * S^2`, same `adder_percentage`, with `piFactor = (1 - pi_effect) + pi_effect * hype` (hype = +0x118, not the release interest). If the movie is created as a back-catalog entry (`MakeMovie(0)` -> `AIMovie_CreateIncome(..., pool_zero = true)`) the pool is set to **0** (no income). Released AI movies also push their genre into the genre saturation tracker (`Release_PushGenreSaturationEntry_AI`, section 3e).
* **When a studio releases** (`CStudioAI_DecideAndReleaseMovie`, `0x5154A0`, tuned by csv `Movie release desire threshold 0.5`, `Success target range width 0.5`, `Difference target 0.1`/`multiplier 3`, `Deviation target 0.2`/`multiplier 12`, `Minimum/Maximum time between releases 0.5/2` years): a desire value from how far the studio's recent success differences (`CStudioAI_MeanSuccessDifference`, `RmsSuccessDifference`) are from the targets, ramped up by the time since its last release between the min and max gaps; **a movie is made when it exceeds the 0.5 threshold** (roughly one release per 0.5-2 game years per studio). Exact weights of the desire formula are read from globals `0x104BD70-0x104BD98`, not traced here.
* `AIMovie_...` names are mine: `GetStudio` `0x5A2AA0`, `GetSuccess` `0x5A2C10`, `CreateSuccess` `0x5A2AF0`, `CreateIncome` `0x5A3240`; `0x5A3EA0` (called after the success is created) feeds the result back into each cast star's stored value (vslots 0x23C/0x244) - purpose not decoded.

### 3ab. Star rating: the full formula (`CStar_ComputeStarRating`, 0x591720) **[code + config; two components still open]**
`rating = clamp01( S + base )`, where `base = star+0xCCC` (an unweighted term) and `S` accumulates `clamp01(weight_i * component_i)` for nine components with a clamp to 0..1 after each addition. Weights are read from `global.ini` into `StarRatingWeight_*` (renamed): **movies 0.174, salary 0.139, performance 0.139, image 0.104, trailer 0.104, entourage 0.104, press bar 0.102, relationships 0.07, awards 0.07** (they add to 1.006). Components (all clamped 0..1 and cached on the star; for stars of other studios the game uses cached values instead of recomputing):
- **salary** (`CStar_ComputeSalaryComponent`): mapped from the star's current salary through a curve (not decoded further).
- **relationships** (`CStar_ComputeRelationshipsComponent`): over the other stars of your studio, `sum((r-0.5)*2 * (otherLevel*0.5+0.5) * k)`, with `r` the pairwise relationship value.
- **image** (`CStar_ComputeImageComponent`, 0x5909C0): built from the costume value (`CStar_ComputeCostumeImageValue`, 0x58FB60: how fresh the current costume is against its wear dates, then adjusted by cosmetics: `femalebeard` -0.65, `maleeyeshadow` -0.1, `malelipstick` -0.1, `malenailvarnish` -0.05 from `global.ini [star]`), the body appearance (`weight`/look) scaled `* 0.6 + 0.4`, and a second appearance term from virtual slot 0x238; the terms are then combined by a small formula over the minimum of the two plus a function of each (not decoded in detail).
- **trailer** (`CStar_ComputeTrailerComponent`): for your own stars the value returned by virtual slot 0x268 (the star's trailer quality); otherwise the cached value (`+0xD30`).
- **entourage** (`CStar_ComputeEntourageComponent`): number of entourage members x **1/6** (so six members give the full value).
- **awards** (`CStar_GetAwardsRatingComponent`): number of awards the star has won x **0.526** (two awards cap it), cached with the date it was computed.
- **movies** (`CStar_GetMoviesComponent`, virtual slot 0x240): a decaying value (`DecayValue` at `+0xBD0`), see below.
- **performance**: a decaying value kept on the star (`DecayValue` at `+0xBDC`, read by `DecayValue_GetClamped01`), see below.
- **press bar** (`PressBar_GetClampedValue`): the value of the star's press bar object (`+0x344`), the bar the publicity room fills.
Practical reading: about 1/6 of the weight is directly buyable (salary 0.139), 1/10 each is entourage (hire six staff), image (fresh costumes, no cosmetic penalties), trailer and press bar (publicity sessions), awards cap quickly (two awards give the full 0.07), and the two biggest terms, movies (0.174) and performance (0.139), come from the star's film record.

### 3ac. What feeds the two biggest star-rating components (movies 0.174, performance 0.139) **[code + config]**
After a film is released the game updates every member of its cast and its director: `CProject_ApplyReleaseToCastRatings` (0x5AE9C0, for the player's films) and `AIMovie_ApplyReleaseToCastRatings` (0x5A3EA0, for AI films) call two virtual functions of `CStar`: **`CStar_AddMovieRating(S)`** with the film's success `S` (`CProjectSuccess_GetClampedSuccess`, the validated success value of section 2, clamped 0..1) and **`CStar_AddPerformanceRating(p)`** with the star's mean performance score over the film's shots (`CProject_GetMeanPerformanceForPerson`). Each call adds `clamp01(ratingsmultiplier * value)` = `0.4 * value` to the star's decaying value (`+0xBD0` for movies, `+0xBDC` for performance), and each value then decays exponentially with the half-life `ratingshalflife` = 10 (game years, the same `DecayValue` machinery as boredom). The performance call also gives the star a grudge update `likereleasemovie` +0.3 (recovering at `forgivereleasemovie`, see 3y), so releasing a movie with a star in it improves that star's feelings as well as their rating. Examples: a cast member in a film with S = 0.8 gains 0.32 on the movies value immediately (before the 0.174 weight, i.e. +0.056 of rating); two such films within a few years push the value near 0.6, three near 0.9, and the value falls to half after ten years without new films. A flop (S = 0.3) adds only 0.12. So the way to raise a star's rating is a steady run of high-S films with them in the cast, and keeping them acting well (shot performance) feeds the second term. `CStar_AddGenreBoredom` (virtual slot 0x24C) is the third update on release: it adds `genreboredomboost` 0.1 to that star's boredom for the film's genre (3c).

## 3ai. Save-game format (MVSaveable) and TMRoom

**Save mechanics.** One global mode word (`DAT_010583e0`): 0 = writing, 1 = reading. All `SLVAR_*` helpers branch on it: `SLVAR_Raw(ptr, size)`, `SLVAR_String`, `SLVAR_WString`, `SLVAR_Float`, `SLVAR_Array`. Each saved field begins with `Saveable_BeginVariable("Name")`: when writing it emits a 3-byte marker (0x0A 0x23 0x58 as stored) followed by a 4-byte hash of the name (`FUN_009f3c40`), then the data; when reading it checks the hash at the expected stream position and, if it does not match, logs "failed to locate variable '<name>' at expected position in save game. Will try to scan ahead" and scans forward (so saves tolerate added/removed fields). Strings are saved as 4-byte length + bytes; wide strings as (len*2+2) bytes. The write buffer is a growable array (`SaveBuffer_Append`, grows in 0x2000 steps). Pointers are saved as object ids (`Save_LookupIdFromAddress`); unresolved ones are processed afterwards (`Save_ProcessDeferredPointers`). Objects are written by `*_Serialize` functions (e.g. `CProject_Serialize`, `CStar_Serialize`, `TMRoom_Serialize`): header (class name string), pointer-map entry, object id, virtual save body, footer.

**TMRoom** (`TMRoom.cpp`) save variables (offsets as passed, sub-object base): PFloorPlan, BUseIndividualScenes, SoftObjectLimit / MediumObjectLimit / HardObjectLimit (+0x174/+0x178/+0x17c), IconName, RoomName, DesireName, TheActivity, LastActivity, MyIndex, PParentAsset, BIsEnabled, BSnapsToIcon, SL_CurNum_Display / SL_MaxNum_Display / SL_Display_Numbers, and an `ObjectsIn` array (the occupants). A room loads an interaction scene `data/scene/interactions/ai_<roomname>.flm` (`TMRoom_LoadInteractionScene`), tracks occupants in a 0x18-byte-stride vector (+0xf8), limits them by `TMRoom_SetMaxOccupants`, and shows selection state through submesh highlight colours (`TMRoom_SetHighlight*`).

## 3aj. WWindow (UI) and LSWF (Flash UI) notes

## 3ao. GameTime / Timer / GameClock cluster (0x43B490-0x43B9C0)

- **Time is a single float counted in days.** `Time_FromYears(y)` = y * 365 (global 0xD18F74 = 365.0), `Time_ToYears` = days * 0xD18F78 (1/365). `Time_FromYearsPlusDays(y, d)` = y*365 + d. Arithmetic is plain float: `Time_AddInPlace`, `Time_SubInPlace`, `Time_Plus`, `Time_Minus` (out-parameter forms) and the comparisons `Time_Equals`, `Time_NotEquals`, `Time_IsGreaterThan` (this > other), `Time_IsGreaterOrEqual`, `Time_IsLessThan`, `Time_IsLessOrEqual`. `Time_SetZero` clears. A date such as 1 Jan 1950 is therefore about 1950 * 365 days; the float at global 0xE4FA4C is used throughout as a reference time ("now" in many call sites; its static initial value is 693500.0 = 1900 * 365) - confirm at runtime before treating it as the current date.
- **Timer** (16 bytes: interval, last, counter, mode): `Timer_IsElapsed` returns true when the interval has passed in real-time ticks (`DAT_0104CDF4+0x3c`, milliseconds) or, in counter mode, after the given number of calls; `Timer_Init(mode)`, `Timer_FillCounter`, `Timer_GetIntervalTimes100`.
- **GameClock** (the in-game date driver): `GameClock_Update` advances the clock by one tick (`GameClock_AdvanceTick`: adds 1/ticksPerDay of a day and reports when the whole-day part rolls over); on rollover the weekday advances `(w+1) % 7`, then `GameClock_UpdateTicksPerDay` recomputes the pace (+0x14, ticks per day) from the current year: constants 0xE4FA38 = 4, 0xE4FA3C = 20, 0xE4FA40 = 1900, 0xE4FA44 = 1960, 0xE4FA48 = 0.05776, exponential between 1900 and 1960 and constant after 1960. The exact meaning of the pace curve (whether 4-20 ticks/day get faster or slower with the years) is unverified; read the sign of the exponent before relying on it. `GameClock_GetTicksPerYear` = pace * 365. `g_GameClockAltMode` (0xF87D90) switches `GameClock_Update` to a second counter pair (`SetAltMode` / `ClearAltMode` / `IsAltMode`).
- Small math helpers in the same block: `Math_Exp` (e^x via f2xm1/fscale), `Math_Floor` (forward to a CRT routine, assumed floor), `Math_RoundToInt64_A/B` (thin CRT_RoundToInt64 wrappers).

## 3at. The star's trailer quality (feeds the trailer component of the star rating)

Chain: `CStar_ComputeTrailerComponent` (section 3ab) for a player star calls virtual slot 0x268 = `CStar_GetTrailerQuality` (0x5876E0), which takes the star's trailer facility (virtual slot 0x270, a 3-instruction getter returning the `CFacilityTrailer*` stored at CStar+0xAD8; it is not defined as a function in Ghidra) and calls the facility's virtual slot 0x1CC = `CFacilityTrailer_ComputeQuality` (0x84CD90). The result is clamped to 0-1 and is the trailer term (weight 0.104 in the star rating).

**Trailer quality** (`CFacilityTrailer`, subclass of CFacility / TMFixedAssetLarge):
`T = clamp01( 0.2 * A + 0.3 * B + 0.5 * C )`
- A = (n0 + n1 + n2 + n3) * 0.25 / 16 = (n0+n1+n2+n3) / 64, with four integer counts at +0x55C, +0x560, +0x564, +0x568 (up to 16 each; presumably the number of upgrades / items in four categories).
- B = `CFacilityTrailer_ComputeItemsScore` = clamp01( 1.0 * sum of virtual-slot-0x160 values of the objects in the list at +0x170 ) (the trailer's furnishing items, constants at 0xE5D0B4 = 1.0).
- C = 0 if the trailer is in disrepair (`CAsset_IsInDisrepair`), else (condition * 0.5 + 0.5) * (value at +0x554), where condition is the facility's virtual-0xB8 float (state of repair, section 3q) and +0x554 is a per-trailer level float from its definition.
Constants: 0xD1A794 = 0.25, 0xE5D098 = 16, 0xE5D0A0/A4/A8 = 0.2 / 0.3 / 0.5.
Consequence: a neglected trailer (disrepair) loses the largest term (C, half the score), so repairs matter for star happiness through this term. Items behind B and +0x554 are decoded in 3au; still open: the writers of the four counts; the tracker's STAR_COMPONENTS rows can be checked against T once a game run is available.

## 3au. Trailer term B decoded (possessed assets, ornament impact) and the +0x554 field

**What the list at +0x170 is.** `CAsset_Constructor` (0x534F30) initialises +0x168/+0x16C/+0x17C as an `InList<TMFixedAsset>` (the saved variable at +0x170 is mislabelled `PFloorPlan` in the SLVAR macro). Each asset's owner pointer is `PPossessor` (+0x128), so the list is "assets possessed by this asset": for a trailer, the ornaments/decoration placed in it. `CFacilityTrailer_ComputeItemsScore` calls virtual slot 0x160 on each (node pointer at +8).

**Item value (virtual 0x160).**
- Default (CFacility and most TMFixedAsset subclasses, 0x528030) forwards to slot 0x15C: `CFacility_GetAppealValue` (0x5291C0) = `1.0 * attractiveness(+0x2bc) + 0.5 * condition - 0.5` (condition = virtual 0xB8, state of repair).
- `COrnament` (and `CSponsoredBillboard`) override both slots:
  - slot 0x160 (`COrnament_GetImpact`, 0x48A770) = `slot15C / k`
  - slot 0x15C (0x48C660, not a Ghidra function yet) = `(attractiveness(+0x2bc) / s(+0x430)) * D`, where `D = 1 - 0.5 * (atan(n/2 - k)/pi + 0.5)`
  - `k` = definition field `impacthalfcount` at +0x47c (default 9.0, `COrnament_LoadDefinition` 0x48B190); `s` = +0x430 (initialised to 1.0 in the constructor; writer not found yet); `n` = number of COrnament instances of the same type key (+0x35c) in the whole world, from `COrnament_GetCountOfType` (0x48C5D0; the per-key count map at 0x104A5F8 is rebuilt lazily when the flag at 0xE50978 is set by a constructor).
  - `D` falls smoothly from 1.0 to 0.5 as the number of identical ornaments grows past about `2k`.
- Constants verified from the exe: 2.0 (0xE5098C), 0.5 (0xE50984), 1/pi (0xD1CAE0), 0.5 (0xD1694C).

Per-item value with attractiveness a and default k = 9, s = 1 (D shown, then a-multiplier): n=1: 0.981, 0.109a; n=9: 0.965, 0.107a; n=18: 0.75, 0.083a; n=36: 0.518, 0.058a; n=100: 0.504, 0.056a. So B = clamp01(sum): about nine distinct, attractive ornaments of attractiveness 1 saturate the term, and filling the trailer with copies of one ornament yields less than half value per copy once there are ~36+ in the world.

**+0x554 / +0x558** are set by `CFacilityTrailer_LoadDefinition` (0x84C640, slot 0x1A4) from the definition node: `quality` (clamped 0..1) -> +0x554, `territory` -> +0x558. So term C = (condition*0.5+0.5) * definition quality: the trailer's own tier. The four ints at +0x55C..+0x568 are zero-initialised in `CFacilityTrailer_Constructor` (0x84C9A0); the code that increments them is not found yet (A = sum/64).

Open: the +0x430 writer (assumed 1.0), whether other asset types (non-ornament) can be possessed by a trailer, and the writers of the four counts. Check with the tracker once a run has STAR_COMPONENTS and a trailer's ornament list.

The analogous `Studio_GetCateringSurplusRatio` (0x465F40) = clamp01( (g_TotalCateringCapacity - need) / need ), need = 0.5 * (0.1 N' + 0.05 M'), and `Studio_GetToiletSurplusRatio` (0x466060) uses g_TotalToiletCapacity and need = 0.5 * (0.25 N' + 0.1 M'), with N' = max(N,2), M' = max(M,4).

`CStudioPlayer_UpdateAppearance` (0x518570, formerly `Studio_UpdateEnvironmentScore`; runs from the player-studio tick 0x519450 whenever a timer at +0xA9*4 elapses) writes the studio's **appearance** at studio+0x12C (byte offset; an earlier note said +0x4B0, which was a misread of `param_1 + 300`) = clamp01 of:
- clamp01(0.30 * x1), x1 = `FUN_00452af0(DAT_00f88720)` (not decoded)
- + clamp01(0.25 * lot virtual 0x188) (not decoded)
- - 0.25 * (1 - lot virtual 0xB8) (the lot's condition / state of repair)
- + clamp01(0.05 * catering surplus ratio)
- + clamp01(0.05 * toilet surplus ratio)
- + clamp01(0.05 * decoration ratio)
- - 0.05 * (1 - cleanliness(0x466290))

Constants verified from the exe (0xE52190..0xE521A8, 0xE50418..0xE50434). The consumers of the appearance are decoded in 3aw; the meaning of x1 / lot virtual 0x188 is still open.

## 3aw. Studio appearance and the studio star rating (CStudio_ComputeStarRating)

**Readers of the appearance (studio +0x12C).** CStudio/CStudioAI/CStudioPlayer all share virtual slot 0x80 = getter for +0x12C (0x50AB30, not a Ghidra function). It is read by (a) `CStudio_ComputeStarRating` (0x50AB70) and (b) the advice-tip classes `PIP_PLACING_APPEARANCE_UP/DOWN` (getter 0x958A30 and compare 0x958A50, which also compare the lot's virtual 0x188). A second writer is the smoothing code at 0x513BF0 (adds/subtracts a clamped amount using studio +0x26C/+0x270/+0x274 and a 0.1 factor), so the appearance is moved gradually, not only set by `CStudioPlayer_UpdateAppearance`.

**The studio star rating** (stored at studio +0x130, getter = virtual slot 0x84, 0x50AB60), recomputed every studio tick by `CStudio_ComputeStarRating` (0x50AB70, called from 0x50CC00). Each step is clamped to 0..1:
```
s = clamp01( 0.15 * appearance )
s = clamp01( s + 0.30 * DecayedReputation )               // CStudio_GetDecayedReputation 0x50A860
s = clamp01( s + 0.30 * virtual 0x90 )                    // CStudio_GetMoneyRatingComponent   0x50CFE0
s = clamp01( s + 0.30 * virtual 0x94 )                    // CStudio_GetStarPowerRatingComponent 0x50FC90
s = clamp01( s + 0.15 * virtual 0x98 )                    // CStudio_GetAwardsRatingComponent  0x50D8E0
studio.rating = s
```
- **Decayed reputation** = clamp01( rep(+0x138) * exp(-0.01 * years since +0x13C) ): stored reputation fades 1% per game year in the exponent.
- **Money component**: studio money (virtual 0x24) compared with a six-entry int64 threshold table at 0x104BD38: starts at -0.2, +0.2 for each threshold passed, linear interpolation inside the current bracket (money scale 2^-23), clamped; below the first threshold the result is 0.
- **Star power**: take the ratings of the studio's stars (list at +0x94, `TMCharacter_GetStarRating`), repeatedly pick the highest, add `rating * w` with w = 0.4 for the best star, then 0.35, 0.30, ... (w decreases by 0.05 per star), clamped after each addition.
- **Awards**: number of award entries whose owner (+0xB8) is this studio times 0.1695 (about 1/5.9), clamped.
- Consequence: a fully-decorated, well-kept studio contributes at most 0.15 to the rating directly; decor/appearance is the smallest term and money, reputation and star power dominate.

**Where the studio rating is read** (call sites that fetch the player studio then call virtual 0x84): 0x574AA0 scales it by a 16-bit constant at 0xE531FC (= 5) and rounds (likely the number of arrivals of some NPC type per period, minimum 1 during a tutorial), 0x84E610 blends it with a field at +0x120 for a similar count, 0x8633C4/0x8634C5 (UI), and 0x8F38A0 (a getter object, probably an objective/advice value). These functions are not defined in Ghidra yet, so their exact purpose is unconfirmed.

## 3ax. CLot (save variables, lot-wide metrics) and CShoot crew validation

**CLot** (`Lot.cpp`; `CLot_RegisterSaveVariables` 0x4667E0 then `CAsset_RegisterSaveVariables`): `(int&)CurrentSize` (+0x408), `SL_CamPos` (+0x428, 12 bytes), `SL_CamFoc` (+0x434, 12), `SL_CamZoo` (+0x440), `SL_CamRot` (+0x444), `SL_GameSpeed` (+0x448), `SL_Version` (+0x44C, string). `CLot_PreSave` (0x467910) fills the camera and version fields from the live camera and game. Lot-wide metrics used by the studio appearance of 3av/3aw:
- `Lot_GetCleanliness` (0x466290) = clamp01( 1 - litter / 30 ), litter in the global at 0xF8904C.
- Lot virtual 0xB8 (0x467E80, not a Ghidra function) = mean of virtual 0xB8 (state of repair) over all assets for which virtual 0x10C is true, i.e. the average condition of the lot (this is the `1 - lot condition` penalty term of `CStudioPlayer_UpdateAppearance`).
- Lot virtual 0x188 (0x466310) = clamp01(lot +0x45C). That field is the lot's **layout score**: a routine at about 0x4695A0 (not a Ghidra function) computes a per-asset value in asset +0x19C from a pairwise relation (asset virtual 0x178 between each asset and the others, normalised by the asset count) and stores the mean over all assets in lot +0x45C. Its inputs and meaning (adjacency, aisle clearance?) are not decoded; it contributes `0.25 * clamp01(layout score)` to the appearance.
- `Lot_GetMinAssetMetric` (0x468030) = minimum of asset virtual 0xF0 over all assets, clamped 0..1.

**CShoot** (a scheduled shoot slot; `CShoot_*`): rooms/slots are four vectors of 0x18-byte entries at +0xA8 (role 7 cameraman), +0xB8 (role 8 soundman), +0xC8 (role 10 dolly operator) and +0xD8 (role 12 clapper man) using the staff job numbers of 3ad; the assigned CStaff is stored at entry +0x14. `CShoot_SetShootController` (0x4DC8F0, +0x10C) resizes the four vectors to the shoot controller's slot counts; `CShoot_SetSlotAssignee` (0x4DC880) sets one entry.

`CShoot_ValidateCrewAndCast` (0x4DCB40) checks the shoot and records problems with `ShootProblems_Add` (0x4DC690) into the structure at +0x12C. Problem codes: byte flags 1 (no cameraman found/available), 2 (no soundman), 3 (dolly operator), 4 (clapper man), 5 (cast member/ director cannot be placed), lists for 10 (staff member cannot fill the slot), 11 (star belongs to another studio), 12 (not used here), 13 (star/actor unavailable: virtual 0x1DC true), 14 (costume change needed; `TMCharacter_SetBaseCostume` is applied for cast that pass). The function returns true only if no problem was recorded, and auto-assigns missing crew with `FUN_005B6EE0` (a "find free staff of this role" helper). `CShoot_IsReadyToShoot` (0x4D7060) additionally requires a director, that every cast entry is usable, that the shoot controller's set is ready (virtual 0x164) and that the controller state is 4 (finished) or the project's active controller is ready.
