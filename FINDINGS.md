# The Movies (2005) — Reverse Engineering Findings

Ongoing reverse-engineering notes for *The Movies* / *The Movies: Stunts & Effects* (Lionhead Studios / Activision, 2005–2006), built on the RenderWare engine. Findings come from static analysis of the shipped `MoviesSE.exe` in Ghidra, cross-checked against real game data files extracted with the game's own official `reshoot.exe` modding tool. See the [README](README.md) for scope and disclaimers.

This is a running log, not a polished writeup — sections are added as threads get investigated, and earlier conclusions are explicitly corrected in place when later evidence contradicts them (left visible rather than silently edited, since the corrections are often as instructive as the final answer).

**IMPORTANT CONTEXT CORRECTION**: the actual binary being analyzed is `MoviesSE.exe` (original linker-recorded filename `Movies.exe`), and its embedded VERSIONINFO resource (checked via Windows Explorer Properties, not Ghidra) confirms it's specifically **"The Movies™: Stunts & Effects"** — the 2006 standalone expansion, not the vanilla 2005 base game (file version 1.2.0.0, product version 1.2, copyright 2002–2006). This retroactively explains several things found earlier that seemed like odd naming choices: `sbx_nostunts` and `sitt_skip_stunt_tutorial` in the disabled debug console, `DesireStuntTrain` in the AI namespace list, `CFacilityTrailer`, and the `"stunttrain/DeviceLevel"` string — all are core to this expansion's stunts/effects theme. The underlying engine, `CSystem`, and the `SLREGISTER`/`SLVAR` serialization framework are presumably shared with the base 2005 title, but keep this SE-specific context in mind when something seems oddly specific to stunts/trailers/effects.

Confirmed via the VERSIONINFO screenshot: `"ui/activision_screen.dds"` + `"ui/lionhead_splash.dds"` (boot splash order), registry key `"Software\Lionhead Studios Ltd\TheMovies"`, and a notable string `"LionheadStudiosTheStarMaker"` — **"The Star Maker"** is a real, separate bundled companion tool (per the user, who owns/knows the game) for creating custom "stars" (actors) to import into the main game.

### Star Maker companion-tool integration (traced and closed)

- `Game_CheckStarMakerNotRunning` (`00542aa0`) — startup gate using named mutexes: creates a `"LionheadStudiosTheStarMaker"` mutex first (if it already exists, Star Maker is running elsewhere, refuses to start with `ERROR_CANNOTSTART_STARMAKERRUNNING`), then a `"LionheadStudiosTheMovies"` mutex for the normal single-instance check. Confirms the main game and Star Maker are mutually-exclusive separate processes — presumably because they share write access to the same data files.
- `Game_InitUserDataFolders` (`0056bd80`) — builds/confirms the full `My Documents\The Movies\` folder tree shared by both apps: `Movies\`, **`Starmaker\`** (confirmed real, shared drop folder for custom star data), `CustomCostumes\`, `Saved Games\`, `Radio Music\`, `Movie Music\`, `Movie Sounds\`, `Graphics\Logos\`. Also does startup maintenance — deletes leftover `TMP*.wav` temp audio files from a prior session.
- `FUN_0057bc70` (not renamed — deep in unrelated scene/character setup logic) — fetches the localized `"UI_STARMAKER"` string and feeds it into the same Tannoy player-facing announcement system found earlier for `"TANNOY_NEW_STUDIOOPENED"` (see `CStudioAI_CreateFromTemplateWithAnnouncement`). Likely fires an on-screen notification the first time a Star-Maker-imported custom actor gets used in a scene. Not traced further — the exact trigger condition (first use? every use?) is unconfirmed.

**Conclusion**: Star Maker integration is a real, confirmed, self-contained feature — two separate processes, mutex-guarded exclusivity, a shared file-drop folder, and a UI announcement hook — fully understood without needing to reverse the companion tool's own (separate) executable.

**Why:** This is explicitly a learning exercise for the user (see [[feedback-re-workflow]] for how we split the work). Sessions proceed one function/thread at a time, verifying evidence (error strings, xrefs, struct field reuse, embedded debug source paths) before committing to names, and openly correcting earlier guesses when new evidence contradicts them.

## Key findings so far

- **`.lug`/`.met` audio bank asset format fully mapped**: load pipeline (`LH_LoadLUGAsset` → `LH_LoadGlobalProperties`/`LH_LoadSampleBankTable`/`LH_LoadBankCriteriaInfo`/`LH_LoadRLMParams`/`LH_ApplyRLMParamsToDrivers`/`LH_ExtractResources`) and its save/build counterpart (`LH_BuildLUGAsset` + matching `LH_Save*` functions), format auto-detection (`LH_LoadLUGAsset_AutoDetectFormat` picks old segmented `.lug` vs newer single-blob "META Data" format), up through the public API (`LH_LoadBank` → `LH_TryLoadBank`) into the engine's resource-manager class **`CSystem`** (name confirmed via an embedded `.\CSystem.cpp` debug string).
- **`CSystem`'s per-resource-type dispatch table** found in `.rdata` around `0xd9dfa0`–`0xd9e008`. Contains: audio sample loading (`CSystem_LoadAudioSample_Wav_Ogg`), a build-info block (`CSystem_GetBuildMachine`/`Date`/`Time`/`P4User`/`P4Server`/`P4Location`/`BuildTag`("RND")/`EngineVersion`("6.6.6.7.4")/`ContentVersion`("6.4.8.9.4")), and a 5-codec audio registry (Ogg Vorbis, WMA, MPEG2LayerII, XBox ADPCM, Windows ACM) with two parallel per-codec object families (lightweight name thunks + richer descriptor records — the descriptor constructors' own call sites were never found, likely reached through an unresolved table).
- **Major discovery: an entire disabled developer console/cheat system.** Three shared low-level registration functions (`0x005434a0`/`b0`/`c0`, named `CVarSystem_Register_STUBBED` + 2 unnamed siblings) are single `RET` instructions in this retail build. 100+ named debug commands/cvars across nearly every subsystem funnel through them and are all inert, while the feature code they'd trigger is fully implemented: camera freecam/debug modes, sandbox cheats (`sbx_*`), achievements (`awd_*`), terrain (`gnd_*`), tutorial UI (`sitt_*`), 7 unused Easter eggs (`ee_*` — two confirmed to have matching custom AI behavior assets: `ai_ee_fightclub.flm`, `ai_ee_rabbitsecurity.flm`), asset/building cheats (`ass_*`), and more. No in-game console UI (text input overlay, toggle key, command-line flag) was found anywhere — the whole dev console (UI + registration) appears compiled out via a source-level build flag, not just the registration step. Fully documented via Ghidra decompiler comments at `0x005434a0` (master writeup), `0x005434b0`, `0x005434c0`, `0x0041c240`, `0x0041a610`, `0x0043fb80`, `0x004afa60`.
- **Real internal dev artifacts recovered from embedded debug strings**: source tree `d:\rh\audio\ver06_movies2\libpk\...` (a shared "PK" utility library — `PKCDelegate`, `PKMultithreadCMailbox`, `PKDiskCReadToMailbox`), a Perforce build-fingerprint block, and the confirmed real class name `LHACodecsOggVorbisCCodecInstance` ("LHA" almost certainly "Lionhead Audio") for the Ogg Vorbis decoder.
- **Two audio DSP effect classes identified**, sharing one parameter-name string pool: a filtered delay/echo effect (`Delay`/`Wet`/`Dry`/`Freq`/`Q`) and a parametric EQ effect (`Freq`/`Q`/`MakeUpGain`).

## Codec descriptor thread — now fully closed

Every codec descriptor's vtable slot `+0xc` turned out to be a consistent `CreateInstance` virtual method across all four codecs (found by tracing `acmStreamOpen` for the ACM one, which revealed the pattern). Confirmed real decoder-instance functions for all four:
- Ogg Vorbis: `LHACodecsOggVorbisCCodecInstance_Open` (class name confirmed via embedded `.cpp` path)
- Windows ACM: `WindowsACM_CreateCodecInstance` → `WindowsACM_CodecInstance_Init` (real `acmStreamOpen`/`acmStreamSize` setup)
- MPEG2LayerII: `MPEG2LayerII_CreateCodecInstance` → `MPEG2LayerII_CodecInstance_Constructor`
- WMA: `WMA_CreateCodecInstance` → `WMA_CodecInstance_Init`

## Major discovery: the game's real RTTI-recovered class hierarchy

`list_namespaces` (paginated, `mcp__ghidra__list_namespaces`) reveals **thousands of real, original C++ class names** recovered from RTTI — the actual game class hierarchy (`TM::` = "The Movies" gameplay namespace, `MV::` = a lower-level shared engine library it's built on, plus real DirectShow SDK classes `CBaseFilter`/`CBasePin`/`CBaseRenderer` confirming the codec/video system is DirectShow-based). **Important limitation**: almost none of these namespaces have functions actually associated with them by Ghidra's analysis — `search_functions_by_name` on a namespace/class name usually returns nothing even though the class clearly exists. To find real code for a class found this way, you have to trace in via embedded `.cpp` debug-assert strings, or via `dynamic_cast` call sites that reference `Namespace::ClassName::RTTI_Type_Descriptor` directly (these appear as literal symbols in decompiled output, e.g. `&TM::CStudioAI::RTTI_Type_Descriptor`), not via direct name search.

## Major discovery: TM::CStudioAI — the rival studio economic AI system

Went hunting for the `Desire*` AI namespace family (~50 classes, character need/motivation AI) and hit a dead end — none of those namespaces have any functions attached, no matching strings, no RTTI mangled names found. Pivoted via an embedded `StudioAI.cpp` debug path into a completely different, fully-traceable system instead: **`TM::CStudioAI`** (confirmed by name via a `dynamic_cast` against `&TM::CStudioAI::RTTI_Type_Descriptor`), a sibling of base class `TM::CStudio`. This is the AI-controlled rival/competitor studio economy:

- `CStudioAI_CreateGlobalInstance` (`0041f4e0`) — the first/template instance, created once at process boot from the main init sequence (`FUN_004244a0`)
- `CStudioAI_Constructor`/`_Destructor` (`00517840`/`005172b0`) — real ctor/dtor; confirmed multiple inheritance (primary vtable + a secondary `ISerializable`-style interface vtable at `this+0x64`, confirmed via an adjustor thunk)
- `CStudioAI_LoadTuningData` (`00515e00`) — loads ~25 named economic tuning properties (script quality/burn rate separately for year 1900 vs 2000, star genre experience min/max, marketing level/variance, prestige, research probability curve) from a text-based `[OBJ]`-delimited save/script format
- `CStudioAI_DeserializeObject`/`_PostLoadSetup` (`00514660`/`00513750`) — **corrected name** (was wrongly guessed as `ReloadFromScript`, looked destructor-like at first glance). Full re-check showed it's the generic "deserialize one self-describing object" entry point of a proper object-graph save/load framework: writes `"[OBJ]"` header → writes the object's real C++ type name (via a call into `FUN_00ace3df`, which is MSVC's own compiler-generated `typeid`-support runtime routine, NOT game code — don't rename it) → registers the instance in a pointer→sequential-ID map (`Serialization_RegisterPointerMapEntry`, confirmed via literal debug strings `"ThisPtr alreaday registered"` [sic] and `"Added PointerMap entry of ..."`) → calls the type-specific `Load` (vtable slot `+8`) → writes the `"[/OBJ]"` footer (`Serialization_WriteObjectFooter`) with a mode branch implying the save format has both a text and a binary variant sharing one object model. (The shared `[OBJ]` header writer and the generic no-op vtable filler used by 90+ and 20+ other classes respectively are still NOT StudioAI-specific — don't rename those as if they were.) Lesson: don't trust a guess based on a function's shape alone ("looks like a destructor") — verify by decompiling what it actually calls, since compiler-generated RTTI helpers and named debug strings can completely overturn the first read.
- `CStudioAI_CreateRandomNew` (`00517a40`) — spawns a fresh rival studio with a randomized "personality" (1 of 6)
- `CStudioAI_CreateFromTemplateWithAnnouncement` (`00517b60`) — spawns a rival studio cloned from a template, firing a `"TANNOY_NEW_STUDIOOPENED"` player-facing news announcement
- `CStudioAI_SpawnDueRivalsAndScheduleDates` (`00510440`) — the roster scheduler: walks studio templates, spawns any whose in-game opening date has passed (checking a global linked list of existing studios via `dynamic_cast` to avoid duplicate names), then de-clumps all studios' opening dates so they don't cluster
- `CStudioAI_RosterManager_Constructor` (`0045d2a0`) / `GameSession_InitEconomySystems` (`0045d330`) — ties it together: only spawns rivals when a global flag (`DAT_0104a981`, possibly a sandbox-mode indicator) is false

**Bonus architectural finding**: this revealed the game has **two separate initialization sequences**, not one — `FUN_004244a0` (one-time process-boot bootstrap: cvar system, sandbox mode, camera debug states) vs `FUN_00422750` (per-game-session setup, called both for a fresh game and via the "reload" path `FUN_004b3550` found back in the freecam investigation: studio reputation, city traffic, and the CStudioAI roster manager). `StudioReputation_Constructor` and `CityTraffic_Constructor` (both named during the disabled-debug-console thread) are session-level siblings of the roster manager.

## Major discovery: the full save/load ("SLVAR") serialization framework

Followed the object-serialization framework found via `CStudioAI` up to its actual top-level drivers. Full picture now confirmed:

- **`DAT_010583e0`** is a global **direction flag: `0` = saving/writing, `1` = loading/reading** (NOT text-vs-binary as first guessed — corrected after checking `FUN_004b37e0`, which shows a literal `"Saving Game"` progress string yet sets the flag to `0`). Every serializable class branches on this exact flag between its write and read paths, using the same bracketed text format (`[OBJ]`/`[/OBJ]`, `[HEADER]`/`[STATICS]`/`[OBJECTS]`) in both directions.
- `Savegame_SaveToDisk` (`004b37e0`) / `Serialization_BeginSave` (`004b1e90`) — save path; resets the pointer-map ID counter to a baseline of 1000, clears buffers, sets direction=write.
- `Savegame_LoadFromDisk` (`004b2b40`) — load path; checks the save format against a literal version string **`"ver17"`** (with a migration path via `FUN_0098bd50`/`DAT_010583e8` if it doesn't match), sets direction=read, walks sections in order: `[HEADER]` → `[STATICS]` → `[OBJECTS]`.
- `Savegame_LoadAndRestoreGame` (`004b3550`) — the orchestrator found originally in the freecam investigation (it disables freecam cvar registration while restoring game state) — calls `Savegame_LoadFromDisk`.

### The `[STATICS]` section = the "SLVAR" reflection system

`SLVAR_LoadOrSaveStatics` (`0098d400`) handles three registries, confirmed via literal progress-log strings (`"Loading N Static vars"` / `"...Static lists"` / `"...Static arrays"`):
1. **Static vars** — a named, type-tagged global-variable registry (name string + type tag 0-6 + pointer), dispatched per-entry to one of 7 type-specific load/save functions. This is what "SLVAR" stands for throughout the codebase's debug traces (Static/Script LVar) — confirmed types by their own debug log strings, zero ambiguity:
   - tag 0 `SLVAR_LoadVector3` (`0098af50`) — 3 floats, logs `"Loaded V3"`
   - tag 1 `SLVAR_LoadUint` (`0098bd50`) — logs `"Loaded Uint : "`
   - tag 2 `SLVAR_LoadByte` (`0098a3c0`) — 1 byte, bool-like
   - tag 3 `SLVAR_LoadFloat` (`0098c460`) — logs `"Loaded FLOAT: "`
   - tag 4 `SLVAR_LoadString` (`0098bed0`) — length-prefixed ANSI string, logs `"Loaded String: "`
   - tag 5 `SLVAR_LoadWString` (`0098c0f0`) — wide string variant, logs `"Loaded WString: "`
   - tag 6 `SLVAR_LoadTrackedUint` (`0098c5b0`) — a uint PLUS the current source file+line (reusing the exact same `DAT_010581d4`/`DAT_010581d8` globals `CStudioAI_LoadTuningData`'s "SLVAR CALLED" trace uses) — a debug-traceable variant for error reporting back to the original C++ call site.
2. **Static lists** — a second registry; entries not already tracked get recreated via `FUN_0097dff0` (likely resetting global singleton collections like "all studios"/"all actors" before `[OBJECTS]` repopulates them).
3. **Static arrays** — fixed-size raw C arrays, direct byte-copied in/out based on the direction flag.

This is genuinely core, load-bearing infrastructure for the whole game — every persistent global piece of state in *The Movies* funnels through this one reflection system.

### The `[OBJECTS]` section = polymorphic factory-by-type-name ("SLREGISTER")

The master object-graph loop (`0098cf50`) reads each object's `typeid`-derived type-name string, checks for the `[/OBJECTS]` end marker, reads/writes the object's 4-byte pointer-map ID, then dispatches to `FUN_0098b940` — a **name-to-factory lookup** that walks a registry table (`DAT_01058478`–`DAT_0105847c`) comparing type names and calling a stored constructor-function-pointer on a match. Confirmed via a literal debug string: *`"Failed To match type when loading [X]. Attempting to scan past. Have you SLREGISTERed it?"`* — so the framework's real name is **`SLREGISTER`**, and it gracefully tolerates a save file referencing a class that no longer exists (skips forward with a warning) rather than crashing — real forward/backward compatibility. `DAT_010583dc` doubles as the loading-progress-bar callback, driven by stream position.

**Important limitation discovered**: the `SLREGISTER` table itself has zero write-xrefs anywhere in the binary — it's a `std::vector`-style registry populated by scattered static C++ object constructors (one per `SLREGISTER(ClassName)` macro use, likely hundreds, invoked automatically by the CRT before `main()`), not a precompiled data table sitting in `.rdata`. **Its contents cannot be enumerated through static Ghidra analysis** — they only exist in runtime memory once the game is actually running. Would need a live debugger attached to a running instance to dump the real class list. Don't spend more time trying to find it statically.

**Version migration mechanism**: `Savegame_LoadFromDisk` checks the save's version against a 2-entry whitelist (`FUN_004aff80`, current `"ver17"` + one prior version, exact prior string not confirmed — stored in a runtime-constructed CString object rather than a plain `.rdata` literal). On mismatch it just stashes the old version value in `DAT_010583e8` and **loading proceeds identically** — there's no explicit per-version branching logic anywhere in the driver. The real compatibility mechanism is the format's inherent design: everything is read by name (`SLVAR`'s "does this property exist" checks, `SLREGISTER`'s graceful-skip-on-unknown-type), so old saves missing newer fields or referencing renamed/removed classes degrade gracefully rather than requiring a centralized migration routine.

## `.msh` mesh format — recon started, class name confirmed

Real class name **`MV::MyAsyncMesh`** confirmed via a raw RTTI mangled-name string (`.?AVMyAsyncMesh@MV@@`) — no functions namespaced to it (same limitation as always), and no attached `dynamic_cast` xrefs found either, so this is name-only confirmation so far. The engine's mesh streaming system (`FUN_009de1d0`/`FUN_009dd1b0`) is an async resource cache keyed by filename (tree-based lookup, same shape as other resource caches), routing through per-directory-prefix path rules (`set_`/`fac_`/`lot_`/`p_` prefixes map to different subfolders).

**LOD naming convention confirmed**: base mesh `name.msh`, then `name_l1.msh` through `name_l4.msh` for progressively lower LODs (found in `FUN_00a67bc0`, a vertex-reindexing/LOD-stitching tool, and the `"%s_l%d.msh"` string).

**Two mesh file format variants exist in the codebase**: the real shipped binary format (confirmed via hex, see below), and a separate **text-based format** referenced only by debug/string literals — `"// The Movies generic mesh file format"`, `"[SUBMESH]"`/`"[END_SUBMESH]"` tags, `"Create New MESH %s\n"` — apparently an export/debug-dump variant from Lionhead's tools, not used by any shipped `.msh` (all real files hex-dumped are pure binary from byte 0). Not traced further.

### Binary format — fully confirmed via the actual parser code

Found the real parser by tracing the async load job all the way through: `FUN_009dd1b0` (cache-miss path-resolution) enqueues a job object whose vtable slot 0 is the destructor (`FUN_009da250`) and **slot+4 (address `00d735d0`, resolves to `009e0ef0` — not auto-typed by Ghidra, had to be read directly off the Listing view since no MCP tool exposes raw data bytes) is the real "parse the loaded buffer" callback**. That thunk (now renamed **`MyAsyncMesh_OnLoadComplete`**) calls **`LH_LoadMeshBinary(meshObject, fileBuffer)`** (was `FUN_009deb10`) — a 1359-line function that is unambiguously the actual byte-level `.msh` reader. **`AsyncLoadJob_ExecuteSync`** (was `FUN_009b3530`) is the synchronous loader that does the literal file read feeding it: `operator_new(fileSize)` + `FUN_009d3ca0` (the generic whole-file-read helper also used by the `.pak` reader) to slurp the entire file into one buffer before handing it to `LH_LoadMeshBinary`.

**Whole-file compression check**: `LH_LoadMeshBinary` first checks for a 4-byte ASCII `"zcmp"` tag at the very start of the buffer; if present, calls `FUN_00afb9d0` (a decompressor) and swaps in the decompressed buffer before continuing. None of the real files hex-dumped had this tag, so all samples checked were the uncompressed variant — worth checking a large `set_*.msh` (much likelier to be compressed) if this is revisited.

**Fixed header, confirmed field-by-field by decompiling the actual header-reader `LH_LoadMeshHeader`** (was `FUN_009dadd0`; populates a local struct field-by-field straight from the raw buffer and returns the byte count consumed):
```
0x00  FormatVersion   (dword)  -- MUST equal 10, or FUN_009deb10 aborts immediately (matches every real file: 0A 00 00 00)
0x04  NumTextureNames (dword)  -- drives mesh+0x38 / mesh+0x3c (texture name table, see below)
0x08  NumMaterials    (dword)  -- drives mesh+0x30 / mesh+0x34 (material table)
0x0c  NumSubmeshes    (dword)  -- drives mesh+0x28 / mesh+0x2c (submesh array)
0x10  byte  \
0x11  byte   } four flag/data bytes, purpose not decoded (vary per file: e.g. 0x11/0x12 differ between
0x12  byte  /  a prop with vs. without some feature -- candidates: bounding-volume-present, collision flags)
0x13  byte  /
0x14  byte  -- flag byte; bits 0x38/0x40 get folded into mesh+0xe4 (the flags dword also touched by the
              "has bones" bit found via the exporter) -- likely a skeletal/attachment-related flag byte
0x15  byte  -- another flag/data byte (0x00 vs 0x80 seen between samples -- high bit meaning unconfirmed)
0x16  byte  -- CONTROL byte gating three optional trailing dwords (0xC2 = 1100_0010 in every real file
              checked, meaning bit1/bit6/bit7 are ALL set, so all three optional fields below are present):
                bit1 (0x02) present -> reads dword at current position into a field (0 in every sample)
                bit6 (0x40) present -> reads another dword (0 in every sample)
                bit7/sign  present -> reads a third dword (0 in every sample; this is the dword
                                      immediately preceding the texture-name table, i.e. file offset 0x20)
0x17  byte  -- read but not used by this function
0x18  dword -- optional field A (present per control byte) = 0 in every sample
0x1c  dword -- optional field B (present per control byte) = 0 in every sample
0x20  dword -- optional field C (present per control byte) = 0 in every sample
```
For every real file checked (control byte = 0xC2, all three optional dwords present and zero) this makes the **fixed header exactly 0x24 (36) bytes**, with variable-length data starting immediately at **0x24** — this is the field I originally (wrongly) called the texture name start at 0x20; it's actually 0x24 (confirmed: `p_tent02_rv.dds` begins right at byte 0x24, not 0x20 — the four zero bytes at 0x20-0x23 are the third optional dword, not part of the string).

**Variable-length sections, in order, immediately following the 0x24-byte header**:
1. **Texture name table**: `NumTextureNames` × 32-byte null-padded ASCII entries (e.g. `"p_tent02_rv.dds"`). Each name is resolved to a loaded texture via `FUN_0099bb50`, branching on prefix (`cos_`=costume texture, `head_`=head texture, `hair_`+9th-char `f`/`m`=hair texture, else generic `.dds` load, with a special-case swap to `"dummy.dds"` for logo textures on low-spec). Results stored in a `mesh+0x3c` pointer array, count at `mesh+0x38`.
2. **Material table**: `NumMaterials` × 36-byte (0x24) records, parsed by `LH_LoadMeshMaterial` (was `FUN_009daeb0`) — heavy bit-packed render-state flags plus two texture-table indices (0xff=none). Stored at `mesh+0x34`, count at `mesh+0x30` (this exactly matches the fields the mesh **exporter** `LH_ExportMeshDebugText` reads when writing `[MATERIAL]` blocks — full closure between reader and writer).

   **Material bitfields fully decoded** (bit-by-bit, not just field boundaries — see the full decompiler comment on `LH_LoadMeshMaterial` at `009daeb0` for the complete derivation). On-disk record is up to 0x18 (24) bytes: `S0`/`S2` (bytes 0/2) = Texture0/Texture1 raw indices; `S1`/`S3` (bytes 1/3) = gated pass-through bytes, meaning unconfirmed; `D1`/`D2`/`D3` (dwords at +4/+8/+0xc) = scattered single-bit flags feeding the in-memory entry's two packed-flags dwords; `D4` (dword at +0x10) = copied verbatim to the material entry's first dword (likely a color/ID, not decoded further); `D5` (dword at +0x14) = present only when `D3` byte2 bit2 is set (true in every real file checked) and becomes the low 3 bytes of the entry's first flags dword. In-memory entry: `+0x00`=D4 direct copy, `+0x08`/`+0x0A`=Texture0/1 raw index, `+0x0C`="TypeCode" enum-like state byte, `+0x10`/`+0x14`=packed flag dwords built bit-by-bit from D1/D2/D3, `+0x18`/`+0x1C`=resolved Texture0/Texture1 resource pointers. Two mesh-level side effects: `mesh+0xe4` bit21 and bit25 (the latter meaning "this mesh has at least one multi-texture material") get set from material flags.

   **TypeCode semantics — fully resolved for the renderer thread.** Found the actual render-time dispatch by walking `IDirect3DDevice9` xrefs (via its backing global `DAT_0105ca44`, since `g_pDirect3DDevice` is itself just a cached copy) rather than trying to trace forward through virtual calls: an already-Ghidra-named function `BuildAndDrawPrimitive` (a billboard/particle-sprite drawer, not mesh-specific) calls `FUN_009911b0(materialPtr)` right before drawing, and *that* function opens with `switch((char)param_1[3])` — `param_1[3]` being exactly the material entry's `TypeCode` byte at `+0xC`. `FUN_009911b0` (now renamed **`LH_ApplyMeshMaterial`**) is genuinely shared infrastructure with ~30 callers across mesh/camera/particle rendering, confirmed real IDirect3DDevice9 vtable offsets throughout (`0xe4`=SetRenderState, `0x104`=SetTexture, `0x108`=GetTextureStageState, `0x10c`=SetTextureStageState, `0x114`=SetSamplerState, `0xb0`=SetTransform — all matching the real documented D3D9 vtable layout), and a switch covering values from 0 up to at least 0x2D(45) (most not reachable from mesh materials specifically). Confirmed meanings for every value `LH_LoadMeshMaterial`'s TypeCode byte can actually produce:
   - `0`/`1` = untextured (stage0 disabled, no texture bound)
   - `3` = textured: binds Texture0 to stage0; if "has texture1" (matEntry+0x10 bit26), adds a second texture stage blending Texture1 (a detail/lightmap-style combine); otherwise plain single-texture modulate
   - `4` = textured, same shape as 3 but a different combine-argument recipe when texture1 is present
   - `5` = textured with a distinct alpha-blend argument recipe — matches the loader's "has alpha" flag (`D1` byte3)
   - `6` = WATER (static fallback): binds the loader's `"eau.dds"` texture with its own dedicated blend recipe
   - `7` = single-texture blend, yet another distinct recipe — visual purpose (glow/emissive?) unconfirmed
   - `0xB`/`0xC` = dual-texture blend using a different combine formula than case 3's texture1 path — matches the loader's `D1` bit2 flag; plausibly a lit-window/glow material given the room-metadata subsystem's interest in `"window"`-named geometry
   - **`0x16` — CORRECTED, was previously guessed wrong.** Originally assumed (from the loader alone, which just clears both texture refs when a global flag `DAT_0105ca74` bit4 is set) that this "hides the material entirely." Reading the renderer's actual case for `0x16` disproves that: it ignores this material's own (cleared) textures and instead binds a **separate global animated water resource** (`"Water.raw"`, loaded once by `Renderer_InitDeviceStateAndResources` into `DAT_01059550`) with live `D3DTSS_BUMPENVMAT` texture-stage states driven by a per-frame-updated bump/wave matrix (`DAT_0105954c`) — a genuinely fancier, procedurally-rippling water render path, not a hidden/no-render one. Real lesson: a loader branch that clears a material's fields is not proof the material becomes invisible — the renderer's own switch case for that TypeCode has to be checked before concluding that.
   - `0x18` = animated/scrolling texture coordinates: loads a 4x4 matrix and advances it by a fixed 1/12-per-frame increment via `SetTransform(D3DTS_TEXTURE0, ...)` — a scrolling-UV material, plausibly for waterfalls/conveyor-belts/flowing surfaces. Matches the loader's `D3` byte0 flag.
   - `0x1B` = textured, but with color AND alpha both driven purely by the texture (`SELECTARG1`/`TEXTURE` for both ops, stage1 disabled) — no diffuse modulation — plus a `SRCBLEND=1`/`DESTBLEND=2` blend pair distinct from water's standard `SRCALPHA`/`INVSRCALPHA`. Matches the loader's `D3` byte2 bit0 flag (a flag independent of the texture1/alpha-count checks that produce 3/4/5). Plausible use: decals or unlit glow-style surfaces that shouldn't be shaded by scene lighting.

   **Confirmed NOT the mesh-submesh draw function** (checked while trying to identify it): `FUN_009e56f0`/`FUN_009e5860`/`FUN_009e5b40`, the three functions sitting immediately after `LH_LoadMeshBinary` in the address map. All three build a *fresh* local material record from scratch and draw a hardcoded quad — none touch a mesh object's actual submesh/primitive arrays (`mesh+0x28`/`+0x2c`). They turned out to be genuine bonus finds in their own right: a shoreline/wet-sand effect (reusing the water blend recipe on a `"land_sand00.dds"` texture with scrolling UVs), a water-surface overlay/reflection effect, and a small decal-quad drawer.

   **Found real mesh-geometry-drawing code, but it's a secondary pass, not the primary one.** `LH_DrawMeshLightProjectorPass` (checked among the other `LH_ApplyMeshMaterial` callers, via a background Agent scan of the remaining ~24 candidates) genuinely walks `mesh+0x28`/`+0x2c` (submesh array) and each submesh's primitive array, calling `DrawIndexedPrimitive` (vtable+0x148) with a real triangle count — confirmed via `LH_GetPrimitiveDrawInfo`/`LH_GetPrimitiveDrawInfo_Impl`, which also reconfirmed `primitive+0x1c`=TriangleCount and `primitive+0x2c`=VertexCount and identified two new fields: `primitive+0x0c` (a back-reference, purpose unconfirmed) and `primitive+0x28` (a resource-wrapper pointer, likely holding the index/triangle-buffer resource built at load time by `LH_BuildPrimitiveIndexBuffer` — not fully confirmed) and `primitive+0x08` low byte = a material/LOD index into the mesh's material array. **However**, the material this function actually binds via `LH_ApplyMeshMaterial` is a *throwaway* one built fresh via `FUN_009910f0` — the same pattern the three ruled-out effect-quad functions used — never the mesh's real per-primitive material from `mesh+0x34`. Combined with a preamble that walks a linked list of "light" nodes (each with a transform matrix + texture, bound via `SetTransform`/`SetTexture` before drawing) gated by `mesh+0xe4` bit14 (0x4000), this is genuinely **a dynamic light/projector overlay pass** — thematically, almost certainly the movie-studio stage-lighting/spotlight-cookie system — not the base textured draw pass. `LH_Submesh_TestLightMask` (called per-submesh before this pass touches it) is a confirmed **per-submesh light-channel mask test**: `submesh+0x24`/`+0x26` (shorts) are "only accept light N" / "accept all lights except N" indices into a light-activity bitmask, `submesh+0x28` bit4 gates on a global "dynamic lighting enabled" flag (`DAT_0105bea0`). This is a nice, concrete confirmation that individual set/building submeshes can be tagged to respond to (or ignore) specific stage lights.

   **FOUND: the primary/base per-primitive draw pass — `LH_DrawMeshPrimitive`.** Reached not through `LH_ApplyMeshMaterial`'s caller list directly, but by following `LH_DrawPrimitive_SoftwareSkin_Single`/`LH_DrawPrimitive_SoftwareSkin_Multi` (two CPU-software-skinning variants found while chasing the light-overlay pass) back to their shared caller, a per-primitive **skinning-method dispatcher** `LH_DispatchPrimitiveDraw`. That dispatcher branches on whether a primitive is "smooth-skinned" (`primitive+0xA` bit0) and whether the current mesh context has bones (`DAT_01050c48+0xa0` bit0), then picks one of three implementations per branch based on capability/debug flags — `LH_DrawPrimitive_SoftwareSkin_Single`/`LH_DrawPrimitive_SoftwareSkin_Multi` are CPU-software-skinning fallbacks gated by a debug toggle (`DAT_0105eaf4`); the **normal/default case** (what every ordinary static prop like `Data\meshes\p_*.msh` actually uses) is `LH_DrawMeshPrimitive` (single/no-bone primitives) or its multi-bone sibling `FUN_00a6fad0` (not individually inspected).

   `LH_DrawMeshPrimitive` confirms the full real-material pipeline: `piVar9 = *(int*)(DAT_0105eb48+0x34) + (primitive+8 & 0xff)*0x24` — `DAT_0105eb48` is the globally-cached "currently rendering mesh" pointer, `+0x34` is the confirmed `MaterialArray` field, and `(primitive+8 & 0xff)` is the confirmed per-primitive material-index byte — then `LH_ApplyMeshMaterial(piVar9)` (the real material, not a throwaway) followed by `DrawIndexedPrimitive` (vtable+0x148) using the triangle count from `LH_GetPrimitiveDrawInfo`. This closes the loop: loader → header → materials → renderer dispatch → light-overlay pass (ruled out) → skinning dispatcher → **base draw pass**, fully confirmed end to end.

   Two things spotted in `LH_DrawMeshPrimitive` but not decoded further if this is revisited: an LOD cross-fade branch (delegates to `FUN_00a704b0` when blend factors are present) and a large branch (gated by primitive flag bit `0x1000`) that accumulates up to 9 "area"/lightmap positions from the mesh-context global before drawing — plausibly a per-room dynamic lightmap/light-probe blending system, which would tie back nicely to the still-undecoded room/window metadata block in `set_*.msh` files.

   For completeness, all functions ruled out while chasing this: `FUN_00a598e0`/`FUN_00996020`/`FUN_00997c00`/`FUN_008d97f0`/`FUN_00a578d0` (particle/decal/billboard quad-strip builders), `LH_DrawPrimitive_SoftwareSkin_Multi`/`LH_DrawPrimitive_SoftwareSkin_Single`/`FUN_00a6d8d0`/`FUN_00a6e300`/`FUN_00a6ef20` (other per-primitive draw variants — some now identified above as skinning-tier siblings, not throwaway effect drawers as first assumed), `FUN_00a6fad0`/`FUN_00a71180`/`FUN_00a704b0` (per-primitive effect dispatchers/routers), `FUN_00a6c6e0` (single fixed draw using a prebuilt material), `FUN_00a24a80`/`FUN_00a24930`/`FUN_00a24be0`/`FUN_00a24d70` (a different "dynamic vertex" struct — terrain/decal quads), `FUN_00a4c710` (billboard/point-array drawer), `FUN_0097e660` (trivial render-state toggle wrapper), `FUN_00aac380` (single fixed draw, likely a line-strip/lightning effect), `LH_StudioCamera_UpdateAndRender` (too large to fully check, only one `LH_ApplyMeshMaterial` xref).
3. **(`set_*.msh` only) Room/window metadata block — fully decoded.** RoomCount comes from the header's third optional trailing dword (always 0 in the plain prop files checked earlier — that's *why* it looked unused; it's building-mesh-specific). `mesh+0x70` points to a 0x14-byte holder (`[0]`=RoomCount, `[4]`=RoomArray ptr), and `RoomArray` is `RoomCount` × 0x90-(144)-byte records:
   - `+0x00` RoomIndex (dword) — filled in only *after* sorting, zero while the file is still being read
   - `+0x04`–`+0x23` (32 bytes) Name — read straight from the file, null-padded ASCII (the same fixed-name-buffer convention as texture names and `.pak` entries)
   - `+0x64` a pointer to a **small indexed polygon chunk** — `VertexCount`+`IndexCount`+a `Vector3` array+a triangle-index array, read via `LH_LoadAuxPolygonChunk`. **Correction**: I first assumed this was a descriptive text string; decompiling `LH_LoadAuxPolygonChunk` itself showed it reads two counts then `count*12` bytes of floats and `count*6` bytes of index triples — the room's actual floor/boundary shape, a tiny geometry chunk in the same format as the main mesh, not text.
   - `+0x6c` Flags (dword): bit1(`0x2`) = name starts with `"room_"`; bit3(`0x8`) = name contains `"window"` anywhere (via `FUN_009ac120`, a confirmed `strstr` equivalent); bit0 is an "unclassified" sentinel cleared once either match is made

   Processing order while loading: classify each room by name → swap array slot 0 with the *last* `"room_"`-matching entry (guarantees slot 0 holds a real room rather than a window/generic entry) → for `set_`-prefixed mesh filenames specifically, **bubble-sort adjacent rooms by the numeric suffix in their name** (extracted via `FUN_009b7af0`, a leading-digits-to-int parser reading from name-offset+9, i.e. right after `"room_"`) — giving natural numeric order (`room_2` before `room_10`) rather than alphabetical — → two finalization passes, the second of which stamps the final `RoomIndex`.

   This is genuine per-room dynamic-lighting/interaction metadata for building interiors, and it ties directly into two things confirmed later in the rendering-side investigation: the base draw pass `LH_DrawMeshPrimitive`'s per-room "area"/lightmap-position accumulation (up to 9 areas, read from the current mesh-context global), and `LH_Submesh_TestLightMask`'s per-submesh light-channel masking (`submesh+0x24`/`+0x26` = only-accept/exclude specific light indices). The mesh object also has up to 5 optional auxiliary polygon chunks in the same `LH_LoadAuxPolygonChunk` format, at `mesh+0x50`/`0x54`/`0x58`/`0x5c`/`0x60`, gated by other header flag bits — purpose of each unconfirmed (LOD/impostor cage? collision hull? sound-occlusion volume?); two of the five read-and-discard their result immediately, suggesting deprecated fields kept only for byte-stream compatibility.
4. **Submesh array**: `NumSubmeshes` entries allocated at `mesh+0x2c` (count at `mesh+0x28`) — this matches the exporter's submesh loop exactly. Each submesh holds one or more **primitives**, each parsed via `LH_LoadMeshPrimitiveHeader` (was `FUN_009dcb40`; a packed-record decoder reading a primitive header with an embedded `TriangleCount` and `VertexCount`).
5. **Per-primitive triangle/index buffer**: `TriangleCount * 6` bytes read (3 × uint16 indices per triangle), built via `LH_BuildPrimitiveIndexBuffer` — this is the exact sequential-uint16 run spotted in the original hex dump (`00 01 02 03 04...`).
6. **Per-primitive vertex buffer — compressed format fully decoded.** `VertexCount * 0x20` (32) bytes on the *in-memory* side always, but **two on-disk encodings exist**, selected by a flag bit: a compact **16-byte-per-vertex packed/quantized** format decoded via `LH_DequantizeVertex`, or a direct/uncompressed path (the only one taken by both real prop files checked so far — worth finding a compressed sample, e.g. a large `set_*.msh`, to cross-check against real bytes). The in-memory 32-byte vertex record itself was confirmed independently via the exporter (`LH_ExportMeshDebugText`): `Pos(3f)@0x00, Norm(3f)@0x0c, UV(2f)@0x18`.

   `LH_DequantizeVertex`'s dequantization math is textbook 16-bit vertex compression, confirmed term-by-term: the compressed record is 8×`uint16` (16 bytes) — `PosX/Y/Z` (offsets 0x00/0x02/0x04) each `LERP`'d between a per-primitive bounding-box min/max; `NormX/Y/Z` (0x06/0x08/0x0a) mapped directly to `[-1,1]` via `2*(val/65535)-1` (no bbox needed since normals are unit-length); `U/V` (0x0c/0x0e) `LERP`'d between a per-primitive UV min/max. The bounding-box reference values come from `LH_LoadVertexQuantizationBounds`, called by `LH_LoadMeshPrimitiveHeader` when a flags byte in **its own temporary parse-staging struct** (a local stack buffer in `LH_LoadMeshBinary`, NOT the persistent runtime primitive object — see correction below) has bit `0x20` set — it copies 14 raw floats (56 bytes) into that staging struct at `+0x1c..+0x54`: the first 10 are exactly `BBoxMin.xyz`/`BBoxMax.xyz`/`UMin,VMin`/`UMax,VMax` (confirmed, used by the dequantizer above); the last 4 floats (`+0x44..+0x50`) are **not** read by the dequantizer at all — unconfirmed purpose, candidates are a second/lightmap UV channel's bounds (plausible given the room/area-lightmap system found in the base draw pass) or a bounding-sphere center+radius.

   **Correction — caught while chasing this further**: I initially labeled these staging-struct offsets as "primitive+0x1c" etc., which is wrong and risks confusion — the rendering-side functions (`LH_DrawMeshLightProjectorPass`, `LH_DrawPrimitive_SoftwareSkin_Single`, `LH_DrawMeshPrimitive`, `LH_GetPrimitiveDrawInfo_Impl`) read a *different*, persistent, heap-allocated (`operator_new(100)`, constructed via `FUN_009d5db0`) primitive object whose own `+0x1c` is `TriangleCount`, unrelated to this loader-local staging buffer. Small offset numbers coincidentally overlapping between the two structs is what caused the conflation. The dequantization math itself is unaffected by this — it was verified purely from the data flow between `LH_LoadMeshPrimitiveHeader`/`LH_LoadVertexQuantizationBounds`/`LH_DequantizeVertex`, none of which depends on the persistent object's layout. Not yet checked: whether any of these 14 floats (or their dequantized results) get copied into the persistent primitive object afterward, or are purely transient to the load step.

**Mesh object field map now confirmed** (combining reader + exporter evidence): `+0x28`=SubmeshCount, `+0x2c`=SubmeshArray, `+0x30`=MaterialCount, `+0x34`=MaterialArray (36 bytes/entry), `+0x38`=TextureNameCount, `+0x3c`=TextureArray, `+0x3d`=a byte flag read early (`local_1e9`-related), `+0x44`=room-name-table pointer (set_* only), `+0x70`=room-list header (set_* only), `+0xe4`=misc bitflags dword (bit0 = has-bones/skeletal, plus several others folded in from header bytes 0x14/0x15).

**Important self-correction from this pass**: earlier documentation of the vertex-quantization block mislabeled its offsets as "primitive+0x1c" etc. — that's actually a temporary stack staging struct local to `LH_LoadMeshBinary`'s parsing, produced by `LH_LoadMeshPrimitiveHeader`/`LH_LoadVertexQuantizationBounds`, and is a *completely different* struct from the persistent heap-allocated (`operator_new(100)`, constructed via `FUN_009d5db0`) runtime primitive object that rendering code reads (whose own `+0x1c` is `TriangleCount`, confirmed independently via `LH_DrawMeshLightProjectorPass`/`LH_DrawPrimitive_SoftwareSkin_Single`/`LH_DrawMeshPrimitive`/`LH_GetPrimitiveDrawInfo_Impl`). ## `.pak` archive format — fully confirmed via code, plus a bonus discovery

**Real class names confirmed via a debug string** (`"Couldn't open MV::CPak::CLoader\n"`): **`MV::CPak`** with a nested loader class **`MV::CPak::CLoader`**.

**Bonus discovery: the retail exe contains Lionhead's own internal Pak-file authoring tools, fully intact and dead-code-only.** `FUN_00ab4df0` is a complete "Pak File Writer" (`AllocConsole`, sets console title `"Creating Mega Pack File"`, prints `"The Movies Pak File Writer"`, ends with `MessageBoxA("Finished Creating Pak File", "Pak File", ...)`), and `FUN_00ab19e0`/siblings (`FUN_00ab2c30`, `FUN_00ab3350`, `FUN_00ab4270`) implement a **Pak Combiner** (merges two `.pak` files into one, de-duplicating by content hash — progress strings `"Combine: PAK A opended"`/`"PAK B opended"`/`"Copies removed"`/`"Merged list created"` [sic on "opended", a real Lionhead typo]). Like the disabled debug console found earlier, **none of these entry points have any static xrefs** — no caller was found (checked `get_xrefs_to` on the writer function directly — zero results), so they're reached only through some unresolved mechanism (likely a command-line switch, given `AllocConsole`/`SetConsoleTitleA` usage — a GUI game wouldn't normally spawn a console window). Worth checking `MoviesSE.exe`'s command-line argument parsing if this thread is revisited.

**On-disk format confirmed field-by-field** by decompiling the actual parse chain (`FUN_00a9be50` → `FUN_00a9b6b0`, which reads the raw loaded file buffer as a flat `int[]` — i.e. `param_1[N]` = dword at file byte offset `N*4` — the cleanest possible ground truth) and cross-checking every offset against a hex dump of the real `Data\pak\premium_costumes0000.pak` (713KB, version-4 format):

**Header** (version 4 — versions 5/6 insert 3 extra dwords at `0x1C` before the entries-table-offset field, not yet checked against a real v5/6 file):
```
0x00  FormatVersion     (dword)  -- 4 in the one real file checked; loader accepts 4, 5, or 6, rejects anything else
0x04  dword              -- 4687 in the real file; meaning unconfirmed (maybe archive/build ID)
0x08  dword              -- 0 in the real file; unconfirmed/reserved
0x0c  NumEntries         (dword)  -- 45 in the real file; drives the entries-table allocation size (NumEntries * 0x38)
0x10  dword              -- 256; used later as a count for a second array of 8-byte elements (string pool index? unconfirmed)
0x14  dword              -- 5; unconfirmed
0x18  StringPoolSize     (dword)  -- 79; byte size of a data blob allocated and copied separately (confirmed via operator_new(this+0x18) + matching memcpy)
0x1c  [v5/6 only, 3 extra dwords -- not present/used for v4]
0x28  EntriesTableOffset (dword)  -- 40 (== 0x28 itself, i.e. the entries table starts immediately after this 40-byte header for v4)
0x2c  dword              -- offset/size of the second (8-byte-element) array
```

**Per-entry directory record — exactly 56 bytes (`0x38`), confirmed by the loop stride in the parser (`iVar7 += 0x38`) matching the hex-observed spacing between real entries exactly:**
```
0x00  ContentHash   (8 bytes)  -- used for the Pak Combiner's content-based dedup; not a plain CRC32 (too wide)
0x08  dword                    -- varies per entry (4687 / 61915 seen); candidate: byte offset or a size, order vs. next two fields unconfirmed
0x0c  dword                    -- varies per entry (108 / 53608 seen); same caveat
0x10  dword                    -- varies per entry (138 / 53816 seen); same caveat
0x14  TypeAndVolume (dword, bit-packed) -- confirmed via FUN_00aafeb0's load-time XOR-merge:
        bits 0-14   : low byte (bits 0-7) is a per-extension type tag, confirmed constant per extension:
                        0x02 = ".ini", 0x46 = ".msh", 0x1e = ".cos" (byte value scheme for other extensions not sampled)
                      : bits 1-14 are reused as a *string-pool offset* (`>>1 & 0x3fff`) ONLY in the in-memory
                        representation built by the Pak Combiner tool when merging multiple archives -- not meaningful
                        for a plain single-part pak read straight off disk (name is inline at +0x18 in that case)
        bits 15-26  : the pak VOLUME ID (0-4095, i.e. 12 bits) -- injected at load time by FUN_00aafeb0 via
                        `field ^= (volumeID << 15 ^ field) & 0x07FF8000`, one fresh sequential ID per physical .pak
                        file opened this session (`DAT_010b9360`, capped at 0xfff = "Too many pak files"). This is
                        exactly why multi-volume archives exist on disk as numbered pairs like `TEX_ALL0000.pak` /

0x18  Name          (32 bytes, null-padded ASCII) -- e.g. "category_premium.ini", "cos_f_90s_und_3.msh"
```

The fixed-32-byte null-padded name buffer is the same convention seen in the `.msh` texture-filename field above and in the `.lug`/`LH_ResourceHeader` `Name` field from the audio format work — a consistent Lionhead-wide idiom across at least three unrelated file formats.

## RESOLVED — opened `FUN_005dd3d0` (the "genre trend/box-office factor" calc). The full mechanism is real, elegant, and genuinely ties historical events to genre popularity — just not via the route either of us originally assumed.

`FUN_005dd3d0(genreID, out_saturation)` computes the per-genre popularity value from **two independent, multiplicatively-combined factors**:

```
FinalPopularity = [(1 - S) * (1 - K) + K] * T
```
where `T` = a decaying historical **trend** value, `S` = a **saturation/recent-supply** value (also returned via `out_saturation`, separately used elsewhere as e.g. `RELEASE_GENRE_POP`'s dampener), and `K` is a tuning floor constant. High saturation dampens an otherwise-high trend toward a floor; an unsaturated genre gets its full trend value.

**Factor T — the historical trend, decaying exponentially toward neutral (0.5):**
- Lives in a real, named, already-partially-identified singleton class: **`AudienceTaste_Constructor`** (`0x00523c50`, real object ctor `FUN_00523a60`, global instance `DAT_0104c414`) — this is `TM::CAudienceTaste` or equivalent, and it registers a debug-console command `"taste_show"` (matches the giant SITT command dispatcher pattern found during the radio side-thread — worth trying in-game with the debug console if anyone wants to literally watch this value).
- **`AudienceTaste`'s constructor (`FUN_00523a60`) loads `data/rule/timeline.csv` a SECOND time** (via `FUN_00523090`, passed the literal string `"timeline"`) — independently of the `FUN_0078f5b0` loader that builds `CNoduleEvent` UI objects and independently of the actor-generation reader (`FUN_00595970`/`FUN_00a1db90`) found earlier. **This is the third, previously-unknown consumer of `timeline.csv`.**
- It reads the `[constants]` section (`halflife`/`spread`/`fullspread` — the exact fields seen when the file was first extracted) to compute a proper `ln(2)/halflife` exponential decay rate, defaulting to `halflife=4` (in-game years) if the CSV constants aren't parseable.
- It reads the `[timeline]` header row to enumerate every data column (`genre_action`, `genre_comedy`, `genre_horror`, `genre_romance`, `genre_sci-fi`, plus `technology`/`opinion_smoking`), registering one time-series slot per column name in `AudienceTaste`'s internal map (`this+100`).
- **For every event row and every non-blank cell, it pushes a dated `{date, value}` entry (`FUN_00522490`) into that column's time series.** Confirmed via `get_xrefs_to` that `FUN_00522490` has exactly **one** caller in the whole binary — this loader — so the trend series is seeded **once, at boot, entirely from `timeline.csv`'s historical events**, never touched again afterward.
- At read time (`FUN_005216e0`), the current trend value for a genre is computed by finding the most recent entry at-or-before the current in-game date and applying `2^(-elapsed_years / halflife)` exponential decay, blending the entry's stored value back toward the neutral baseline `0.5` as time passes since that historical event. No entries at all (or entry too old) → flat `0.5`.
- `FUN_005217e0` scans every genre's current `T` value and returns the ID of the highest — this is almost certainly the function behind the GameFAQs guide's *"right click your Scriptwriting Office to find out what's the most popular Genre at the moment"* tip; also used by `FUN_0047f9f0` to fire a notification when the most-popular genre changes.

**Factor S — box-office-driven saturation, a completely separate singleton:**
- A generic per-key statistics tracker created by `FUN_0044bc70` (global `DAT_00f88680`, capacity 1000), queried by genre via `FUN_0044c700`/`FUN_0044d270` and pushed to via `FUN_0044d120`.
- **Confirmed fed by movie releases**: `FUN_005aeb60` (called from the release-outcome processor `FUN_005af7c0`, right after the cast-fame-update function `FUN_005ae9c0`) pushes an entry (`FUN_0044d120`) tagged by the released project's genre every time a movie completes its release cycle — i.e., **recent production volume in a genre dampens that genre's effective popularity**, independent of how good the historical trend looks.

**Bottom line, fully closing the original question**: historical Timeline events mechanically affect genre popularity through **two independent, confirmed-real channels** — (1) biasing newly-generated actors' genre affinity stats (found earlier, `FUN_00595970`), and (2) seeding a decaying per-genre "cultural trend" time series at boot (`AudienceTaste`, found this session) that gets read every time a movie releases and multiplicatively dampened by how saturated that genre currently is from recent releases (`FUN_005aeb60`'s push into the separate saturation tracker). The GameFAQs guide's claims (genre effects from world events; a "most popular genre" queryable via the Scriptwriting Office) both now have confirmed, traced, mechanical backing — this was never just flavor text.
